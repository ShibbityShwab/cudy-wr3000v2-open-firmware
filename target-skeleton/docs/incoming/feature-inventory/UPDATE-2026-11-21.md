## Corrections to the original matrix

- MAC duplication: NOT a blocker. LAN ports (eth0/eth1/eth2) intentionally share the factory base
  MAC and eth3 (WAN) is base+1 - the vendor rule recorded in the DTS address-plan comment (rootfs
  board.d 02_network + 99_fixwan). The original report's multi-port blocker entry is withdrawn;
  multi-port link tests and native switch forwarding remain.
- Thermal: root-caused, not fixable with current evidence. The tvsensor temperature register at
  0x14900500+0x24 reads 0x00000000 (block otherwise zero except +0x10=3); the vendor formula turns
  raw 0 into -368000 mC, which is <= THERMAL_TEMP_INVALID, so the thermal core returns -ENODATA.
  The vendor devicetree marks the sensor disabled and no enable/trim sequence is decoded.
  Decision: thermal telemetry unsupported on 6.18.
- RTC/I2C/USB remain absent per DT+config and vendor evidence; SPI is NAND-only; PCIe stays
  disabled (Wi-Fi endpoints are vendor-only). Wi-Fi: vendor-only on 5.10, no 6.18 driver, declared
  unsupported without GPL source (see ../../wifi-recon).

## Install-path finding (2026-11-21)

The manual stock-mediated install path keeps working: write kernelb via mtd from the stock telnet
shell, ubiformat rootfsb, selector 0x11, reboot. Verified again today for image 7421bb7a (kernelb
sha 5632ccdb..., rootfs part sha 52977160...): 2 CPUs after boot. However
tools/first-install-stock.sh cannot run on this unit as written: it requires an SSH transport to
the stock system, and the vendor image has NO dropbear and no opkg (opkg not found); installing the
project key into /etc/dropbear/authorized_keys and starting our target dropbear on stock fails
(Early exit: Bad buf_getptr when generating host keys). Its read-back step also streams binary
rootfs bytes over the transport, not usable over telnet. Options: install a working SSH server on
stock first, or add a telnet+base64 transport with binary-safe readback. Until then the install
path is [V] manual (repeated, evidence in the ledger) and the automated tool is host-side untested.

Also note the selector behaviour observed today: writing next_pair a from OUR image works (cell
reads 0x10) but the boot-pair recorder re-records the running pair on the next boot, so a warm
reboot can return to pair B. The reliable stock switch is the stock-side cell write + stock reboot.

## Follow-up: automated install tool is now verified

The stock-SSH limitation above is worked around by a new bench tool,
tools/stock-telnet-install.sh (+ tools/telnet-exec.py), which performs the same measured install
path over the stock root telnet shell. End-to-end run on 2026-11-21:
- image 7421bb7a members uploaded to stock and sha256-verified on device;
- inactive pair b kernel slot written (read-back sha 5632ccdb...) and rootfs slot ubiformat OK;
- active pair a kernel slot sha (04d1228a...) unchanged before/after;
- selector cell moved to 0x11 and verified, stock rebooted;
- our 6.18 image answered: 2 CPUs online 0-1, six oem:green LEDs, /dev/input/event0, no errors.
The tool is read-only by default (--inspect) and needs --apply --attended --recovery-armed.

## Multi-port Ethernet (follow-up)

Only the eth2 jack works on the verified baseline, through the documented CPU-copy
mirror workaround. The far-right bench jack is a LAN port (IPv6 RA from the box
received; host-to-box frames not delivered because the mirror covers eth2 only).
The CPU-copy completion reports port 0 and no confirmed source-port identifier, so
extending the mirror mask alone is not a correct multi-port solution. See
opensource/docs/MULTI-PORT-PLAN.md for the attended source-port experiment and the
decision gate (CPU-copy extension vs native L2/VLAN bridge).
