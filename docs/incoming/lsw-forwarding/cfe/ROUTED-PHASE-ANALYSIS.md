# Routed stock phase analysis (2026-11-22): no flow entries yet - box-terminated traffic does not offload

Capture: stock vendor boot, second adapter on the WAN jack (eth3) with host dnsmasq DHCP giving the
box WAN 192.168.50.115/24, then 20 host<->box ICMP pings and two box->host TCP HTTP GETs (host HTTP
server 192.168.50.1:8080). Files in build/evidence-bench-gates/cfe-stock/ (gitignored):
routed-carveout.bin (sha256 d107093be391ec4d75191cfa7df4c1de7217c73765b2540996be75e1b66967a0),
routed-win10-ifc (b022b9bd...), routed-win11-l2 (85749397...), routed-win12-napt (2563b54e...),
routed-win13-mcc (4d119867...), routed-win14-opp (acbdc79b...), routed-win16-pie (c0cea7d7...),
routed-ctrl (9dcc3f3f... = identical to p0 ctrl), routed-win15-pub (f3b58f7b... = byte-identical
to p0 win15-pub).

## 1. Result: the flow arenas are still EMPTY

Byte-exact comparison against carveout-p0.bin (35310a07...) and p2-carveout.bin (103d7a79...):

- v4 buckets 0x80400000..0x80408000: **0 bytes changed**, still 8192 x 0x017be000.
- v4 arena 0x80408000..0x80448000: **0 bytes changed** (still the empty-state image).
- v6 buckets 0x80448000..0x80450000: **0 bytes changed**.
- v6 arena 0x80450000..0x80500000: **0 bytes changed**.
- No bucket word changed, no 32 B or 88 B slot differs from p0; no IP (host/box either side) and no
  TCP/UDP port (8080/80/53/123) appears anywhere in the flow window.
- napt flow-counter bank (napt+0x40000, 255 x 16 B): **empty** in routed too.
- napt dn_match/up_match counters (0x1014/0x1018) stay 0 -> the engine never matched a flow.
  Only the punt counters move: dn_tocpu appears (0 -> 178), up_tocpu 3426 -> 3592, rx_napt
  3641 -> 4016 (routed totals 4048).
- routed-win15-pub is byte-identical to p0: tagact (still the single delete-tag row), l3intf key/
  data, nhp, car, car_profile and mcc userll are unchanged. No L3 interface / user link list /
  tag reference was installed by routed traffic.
- IFC tab128 and the last engine descriptor are identical to p0; only its counters move:
  rx_total/ifc_hit 8231 -> 8605, ifc_tocpu 29 -> 127, ifc_napt 3095 -> 3225.
- L2 window: only the counter page changes (13966 -> 9793 in the repeated bank, i.e. NOT monotonic
  - the vendor counter banks are snapshot/rotating gauges, keep treating them as volatile).
- mcc: only counter words (+0x1000/+0x100c/+0x1010/+0x1028/+0x1030/+0x6000/+0x600c, 14 bytes).
- opp: only a few queue/stat words (+0x1000/+0x100c/0x458xx/0x488xx, 14 bytes).
- pie: 51 bytes in pages 0x2000/0x3000/0x3500/0x5000 (descriptor/ring fields), no class table
  change visible in this window; classes remain 0/0x25/0x4d from the UART matrix.
- queue window: 3,624,499 bytes changed vs p0, same live cell/ring churn as p2.

## 2. Why no entries: the traffic never went THROUGH the box

The generated traffic terminated at the box or was originated by it:
- host->box ICMP pings hit the box WAN IP 192.168.50.115 directly -> NAPT up/down punt to CPU
  (dn_tocpu/up_tocpu), no forwarding decision, no flow.
- box->host HTTP GETs are locally generated by the box (WAN source), so the engine just emits them
  through the WAN port; no forward/NAT decision either.
A NAPT/flow entry exists to accelerate **forwarded** traffic (LAN->WAN or LAN->LAN through the
box). None of the captured traffic was forwarded, so the CFE had nothing to install. This explains
the empty arenas and is consistent with the zero dn_match/up_match counters.

## 3. Next minimal phase (the decisive one): forwarded traffic through the box

Use network namespaces on the bench host so one physical adapter acts as a remote WAN host and the
other as a LAN host; then the traffic must be routed/NATed **through** the box. Example for the WAN
NAT direction (adapt interface names/IPs; LAN_IF = LAN jack NIC, WAN_IF = second adapter):

    # host: LAN NIC (LAN_IF, 192.168.10.44/24 attached to a LAN jack), WAN NIC (WAN_IF)
    sudo ip netns add wan
    sudo ip link set WAN_IF netns wan
    sudo ip netns exec wan ip link set WAN_IF up
    sudo ip netns exec wan ip addr add 192.168.50.1/24 dev WAN_IF
    # DHCP + HTTP server for the box WAN, inside the namespace:
    sudo ip netns exec wan dnsmasq --interface=WAN_IF --dhcp-range=192.168.50.100,192.168.50.150,12h --no-daemon &
    sudo ip netns exec wan python3 -m http.server 8080 --bind 192.168.50.1 &
    # root: send the WAN subnet through the box LAN interface -> forwarded + NATed traffic
    sudo ip route add 192.168.50.0/24 via 192.168.10.1 dev LAN_IF
    ping -I 192.168.10.44 -c 50 192.168.50.1
    curl --interface 192.168.10.44 http://192.168.50.1:8080/   (2-5 times)
    # then dump carveout + win10-ifc + win12-napt + win11-l2 + win16-pie (+ win13-mcc, win15-pub)
    # immediately, and again 20-30 s later.

Expected if the vendor flow engine is active: dn_match/up_match become non-zero, flow_cnt bank
fills, buckets/arenas change, and the 32 B/88 B slot encoding becomes readable. If the arenas stay
empty even for true through-traffic, the stock OpenWrt config is likely running with hardware
offload disabled (no CFE userspace/acceleration hook), and the only route to the entry encoding
becomes a controlled insert probe on our image (W23: one benign flow via the decoded NAPT command
sequence, then a carveout dump) - record that as the M2-A fallback.

Second variant (LAN-to-LAN through the bridge), since the lead can move the second NIC to another
LAN jack:

    sudo ip netns add lan2; sudo ip link set NIC2 netns lan2
    sudo ip netns exec lan2 ip link set NIC2 up
    sudo ip netns exec lan2 ip addr add 192.168.10.55/24 dev NIC2
    # host root: force .55 via the box LAN (eth2) rather than the local stack
    sudo ip route add 192.168.10.55/32 via 192.168.10.1 dev LAN_IF
    ping -I 192.168.10.44 -c 50 192.168.10.55     # bridge-forwarded through the box
    # dump carveout + win15-pub + win13-mcc + win11-l2 + win16-pie

Expected if the vendor hardware bridge is active: userll/userll_ext/l3intf/tagact writes and/or
flow entries appear. If nothing changes, the stock plain bridge is software-only too (which would
support the D1 conclusion that no hardware bridge is needed for the release path).

Also capture at that phase (cheap, read-only): /proc/hsan/cfe/table/flow, mac_stats, intf/dump_intf,
lrn/dump_lib, hook/cnt, and the /proc/hsan/lsw/table/* text - if the CFE shadow prints allocated
rows after through-traffic, it decodes the entry fields for us.

## 4. What was still learned

- The boot-state equality result holds: p0 == p2 == routed == our W22 image over the whole flow
  window; the W22 init reproduces the vendor state byte-for-byte and nothing in this routed phase
  touched it.
- The NAPT punt path is the only path exercised for box-terminated traffic on stock; the counter
  changes (dn_tocpu 178, up_tocpu +166, ifc_tocpu +98, ifc_napt +130) quantify it.
- Counter banks (l2/mcc/opp and several napt words) are non-monotonic snapshot gauges, confirmed
  again (l2 13966 -> 9793, napt option field 655 -> 139 -> 210). Do not use them as free-running
  accumulators in M2 design.
- tagact/l3intf/userll are boot-time defaults only; no routed/box-terminated traffic populates them.

## 5. Limits / M2 status

M2-A is still not decodable: the entry-slot encoding needs real forwarded traffic (next phase
above) or a controlled insert probe. M2-B likewise: no table writes occurred. The M2 verdict is
unchanged (M2 is documentation; W22/M1b is the release path), but the decisive next read is now
exactly one forwarded-traffic stock phase with the netns recipe above, not more static analysis.
