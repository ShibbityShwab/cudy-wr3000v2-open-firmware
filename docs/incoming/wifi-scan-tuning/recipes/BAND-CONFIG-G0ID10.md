# H1 candidate: the g0 id10 scan/channel-config message (CA 0x5FF64)

Research note for the **H1** hypothesis (firmware scan-context not configured by
our host).  This file records the evidence and the **decision not to bind a
speculative g0 id10 builder into the final combined module**; batching stays the
safe path (REPORT.md sec 4.4/8).  All addresses are firmware CA (file offset +
0x40000) and are regenerated by `tools/fw_scan_timing_re.py` (F7).

## How it was found

- The direct H2D dispatch table for **group 0** is at CA **0x10CD08**, 12-byte
  entries `{u32 id; u32 fn(thumb addr|1); u32 reserved}` [V].  Recovered rows:

  | id | handler CA | documented role |
  | ---: | ---: | --- |
  | 1 | 0x43D58 | config-event key dispatch (table A/B) [V, wifi-vap-start] |
  | **10** | **0x5FF64** | **scan/channel-context configuration** (this file) |
  | 12 | 0x6494C | g0 id0xC scan request handler [V] |
  | 15 | 0x62EC0 | STA join sync [V, wifi-vap-start] |
  | 16 | 0x5E28C | STA wait-join [V, wifi-vap-start] |

  Earlier scan-family RE (wifi-scan-d2h) had assumed CA 0x5FF60 from a
  four-byte-misaligned window; the real Thumb function entry is **CA 0x5FF64**
  (the table row is `0x5FF65`) and the dispatch id is **10**.  The bytes before
  it are the tail of function CA 0x5FF06 (pop at 0x5FF5C + nop). [V]
- Our clean-room driver never sends **g0 id10** (grep of the whole provider /
  h2d catalogue: absent).  This is the structural root of H1. [V]

## Handler behaviour (static decode, [V] for reads/writes, [I] for semantics)

Signature: direct g0 message handler `(arg, msg)`: `bl 0x409EA`
(hcc_msg_get_header) -> r4 = header; `ldrb r3,[r4,#3]` -> chip lookup
CA 0x961AE -> module; requires `module+0x4B8` (band object) non-NULL, else log +
return 0x64.  Payload = r4 + 0xC, so payload offset = `[r4+n] - 0xC`.

| payload | header read | role |
| ---: | ---: | --- |
| +0x00 | [r4+0x0C] | **type byte, must be 3**, else the handler ignores the frame (branch CA 0x601DC) |
| +0x01 | [r4+0x0D] | **subtype: 1 = channel/scan-context slot config; 2 = second path (CA 0x60184, not decoded here); other -> log + return** |
| +0x02 | [r4+0x0E] | u16, channel id -> lookup CA 0xD6A1E (band/channel object) |
| +0x07 | [r4+0x13] | slot/band index, must be <= 7 |
| +0x09 | [r4+0x15] | flag byte (nonzero takes the alternate path CA 0x601C2) |
| +0x0C | [r4+0x18] | u16 -> context `+0xFC` (if zero) and `+0x106` (max(1,...)) |
| +0x10 | [r4+0x1C] | u16 -> context `+0x104` |
| +0x12 | [r4+0x1E] | byte -> context `+0x103` (scan mode) |
| +0x14/+0x15 | [r4+0x20]/[r4+0x21] | u16/byte, context `+0xFF` / `+0x100+` fields |

Context writes seen: CA 0x60092 `strh [sb,#0x104]`, CA 0x6009E
`strh [sb,#0x106]`, CA 0x600B2 `strh [r2,#0xfc]` (only if +0xFC was zero),
CA 0x600BA `strb [r6,#0x103]`, CA 0x600C0 `strb [r6,#0xff]`, CA 0x603C6
`strh #0x0101 -> +0xFE`, CA 0x603DC `strh -> +0xFC`, CA 0x603E2 `strh -> +0x104`.
These are exactly the fields the per-channel scan scheduler uses (`link[0xFC]`,
`link[0xFD]`, `link[0xFE]`, `link[0x103]`, `link[0x104]`, `link[0x106]`; see
REPORT.md sec 4.2).  **A single subtype-1 message per scan slot would seed the
context our host leaves at firmware defaults**, including an end index that
covers all 13 channels instead of the default 6. [I]

## Minimal hypothetical frame (NOT implemented, NOT to be fired without a lane)

- family: g0 direct message id **10**, HCC header like other g0 frames
  (`hdr[12]`, no WAL envelope); header[6]=0x0A, total = 12 + payload
- payload: `+0x00 = 0x03`, `+0x01 = 0x01`, `+0x02 = u16 channel id`,
  `+0x07 = slot` (0), `+0x09 = 0`, `+0x0C = end index` (12 for a 13-channel
  plan, or 13?), `+0x10`, `+0x12`, `+0x14`, `+0x15` from decoded semantics
  [U], tail padding.
- sequence: one such message per slot/band **before** the g0 id0xC request,
  after the mode-1 VAP base (module+0x4B8 must exist - it does after the
  bench-validated VAP base).

## Why it is NOT in the final combined module (decision)

1. **Semantics [U]**: the field meanings above are inferred from reads; the
   accepted value ranges (e.g. end index = count vs count-1; u16 channel id vs
   channel number; slot ordering) are unverified.  A wrong value writes a
   scan-context field that the scheduler then trusts.
2. **Fault risk**: this is a *configuration* message in the same firmware
   object family whose wrong-order use has already produced data aborts
   (AP-start: VAP pointer deref without the base; ctx-create precondition).
   A bad g0 id10 on a fresh boot can cost a power-cycle; this lane is host-only
   and the final combined module must stay bench-proven-safe.
3. **Not needed for the target**: batching (scan_req_batch=6) reaches 13/13
   without any new firmware interaction; R0/R1/R7 of TEST-LADDER measure it and
   dispose of H1/H2/H3.
4. **One attended experiment is the right container**: a dedicated H1 lane
   should fire g0 id10 in isolation (single slot, one field change at a time,
   UART + recovery armed), confirm the scan-context readback, then compare one
   13-entry request with and without the config.  Success would let a later
   final module drop batching (or keep it as fallback with `scan_req_batch=0`).

**Recommendation:** keep `scan_req_batch=6` as the shipped default; revisit
H1 (g0 id10) only in a dedicated attended lane with the frames above properly
validated.  The H1 finding is nonetheless important: it explains *why* the
firmware stops at 6 and gives the follow-up lane its exact message.
