**Lane:** wifi-vap-scan (shared task **task-110**), **host-only**, 2026-11-25.

## 0. TL;DR - the ten answers

1. **The four message ids/payload sizes are confirmed from the vendor builder code and the
   firmware receive table**: g0 id7 `hmac_user_add` = 168 B, g0 id8
   `hmac_user_add_notify_alg` = 168 B, g0 id9 `hmac_del_user_notify_dmac` = 12 B,
   g0 id0xC `hmac_enc_scan_send_req` = 508 B. All are group 0 (chip), 12-byte HCC
   header + payload, tag 0x5a5a, total = payload+12.
2. **g0 id7 payload fields are exact** (vendor writes only five fields, firmware reads
   only three): `+0x00 u16 user id`, `+0x02 u8[6] MAC`, `+0x8e u8 user type (2 =
   normal)`, `+0xa4 s8 RSSI (vendor default +100)`; all other bytes are zero in our
   builder (`[I]`; the vendor leaves the message-pool buffer content unwritten).
3. **g0 id8 is NOT a "VAP add"** - it is the capability/rate notification that follows a
   user add (symbol name `hmac_user_add_notify_alg`; firmware copies three capability
   blocks into the user object). The earlier wifi-datapath row "g0 id8 = add vap" is
   **superseded** (corrections register, section 6.1).
4. **g0 id8 payload is exact to the block boundary**: `+0x00 u16 user id`,
   `+0x08 u16 alg/cfg`, `+0x10` 24 B VHT, `+0x28` 44 B HT, `+0x54` 58 B HE
   capability blocks, `+0xa5 u8` (NSS-ish). Block sizes come from the vendor getters
   (`mac_user_get_vht_hdl` 24 B, `_ht_hdl` 44 B, `_he_hdl` 58 B).
5. **g0 id9 is byte-exact** and matches the already-shipped driver attribute
   `h2d_send del_user`: `+0x00 u16 user id` (0x0fff = resolve by MAC),
   `+0x02 u8[6] MAC`, `+0x08 u8 flag`.
6. **g0 id0xC scan request layout is structurally decoded but not byte-complete**: the
   vendor builder `memcpy`s a 508-byte struct from the cfg80211 STA scan builder. We have
   `[V]` offsets for flags (`+0x00/+0x01/+0x02/+0x03/+0x0b`), broadcast BSSID
   (`+0x0c`), 8 x 36-byte NUL-terminated SSID slots (`+0x18`), 42 x 4-byte channel
   entries (`+0x140`), channel count (`+0x1ec`), dwell (`+0x1ee`), scan type
   (`+0x1f0`, firmware rejects 4/8), and the tail constants `+0x1f1=1`,
   `+0x1f2=11`, `+0x1f8 u32=0`; five adjacent flag bytes (setters) and the channel
   `idx` byte remain `[I]`/`[U]` (section 10).
7. **The firmware scan handler is hardcoded to VAP 0**: g0 id0xC handler CA `0x6494C`
   looks up the chip from `hdr[3]`, then VAP id **0** only; with no firmware VAP object
   (our current state) it logs and returns 100 - a graceful refusal, not a fault. It only
   copies the 508-byte payload into the VAP's scan buffer after that check.
8. **Handler risk is low for id7/id8/id9 and moderate for scan**: a full-function decode
   of handlers CA `0x9832C` (id7), `0x96224` (id8), `0x974F8` (id9) shows every
   payload access is at a fixed offset and no payload word is dereferenced as a pointer;
   id0xC's handler validates and copies, but the deeper scan state machine was not fully
   decoded (section 5.4).
9. **Carrier contract is unchanged** (SR node `{devva, (total<<16)|0x6d2b}`, announce
   mailbox id 3, one frame per idea). The builders also expose the node encoder and packed
   producer arithmetic so a driver does not have to duplicate them.
10. **The bench ladder is V1 user-add -> V2 alg-notify -> V3 read-only check -> S1 scan ->
    S2 channel-list scan -> V4 by-MAC delete**, with hard stop rules (section 8). Its
    first blocker is host tooling: the current clean driver can send id9 but not id7/id8/id0xC
    frames, so the driver `h2d_send` grammar needs the three new attributes (or an
    equivalent bench-tooling path) before the ladder can run.

## 2. Carrier and header recap (unchanged, shared with wifi-h2d-frames)

H2D is two layers: a 12-byte HCC frame carried in an ETE SR-ring node, announced through
the mailbox pending bitmap. The builders produce layer B only.

| hdr off | width | value here | evidence |
| ---: | ---: | --- | --- |
| +0x00 | u8 | group = 0 (chip) | vendor builders write the group nibble 0; only groups 0/2 have firmware H2D tables [V] |
| +0x01 | u8 | alloc nibble = 1, high nibble = dst (0) | `hcc_msg_alloc` sets 1; vendor builders BFI the dst nibble [V] |
| +0x02 | u8 | field A: vap id for id7/id8, vap field [0xFA9] for scan | vendor builders copy it from the params/vap object [V]/[I] |
| +0x03 | u8 | field B: chip id for id7/id8/id9/scan (0 = 2.4 GHz endpoint, 1 = 5 GHz) | vendor builders copy it; firmware handlers pass it to the object lookup before doing anything else [V] |
| +0x04 | u16 | total = payload + 12 | `hcc_msg_alloc`; firmware rejects 0 [V] |
| +0x06 | u16 | message id (7/8/9/0xC) | dispatch key [V] |
| +0x08 | u8 | field C = 0 | vendor builders write 0 [V] |
| +0x09 | u8 | dst = hdr[1] >> 4 | `hcc_msg_tx` [V] |
| +0x0a | u16 | transport tag 0x5a5a | firmware receive check (file 0x8699e) [V] |
| +0x0c | - | payload | max 0x674 [V] |

SR carrier: one 8-byte node `word0 = frame devVA`, `word1 = (total<<16)|0x6d2b`, then
the packed producer update, then mailbox id 3 (`out[0] |= 1<<3`, `out[2] |= 1`). The
library exposes `vs_sr_node_encode()` and `vs_sr_producer_next()`; a driver that already
owns the carrier (wifi-h2d-send / wifi-cfg80211) can ignore them.

## 3. Frame specifications

All builders zero-fill the whole frame first, then write only the fields below. Hex
recipes for the bench frames are generated into **recipes/frames.md**.

### 3.1 g0 id7 - `hmac_user_add` (168 B payload; 180 B wire)

Vendor builder: `hi5622v100_wifi.ko` `hmac_user_add` @ 0x8EB34 (2.5.24 build;
0x8E91C in the 2.4.15 build, cross-checked against a local 2.4.15 disassembly;
neither module is committed). Caller chain: `wal_config_add_user` -> `hmac_config_add_user`
(@0x8F2F4) -> `hmac_user_add` -> `hmac_config_send_event` key 0xB2 -> 
`hmac_user_add_notify_alg`.

Header: group 0, id 7, `hdr[2] = params[1]` (vap id [I]), `hdr[3] = params[0]`
(chip/resource id [I]), dst nibble `= params[2]` (0), field C 0.

| payload off | width | field | evidence |
| ---: | ---: | --- | --- |
| +0x00 | u16 | user id | vendor writes it from `hmac_user_alloc` result; firmware reads it as the first payload word and allocates/looks up the user object [V] |
| +0x02 | u8[6] | MAC address | vendor copies the caller MAC; firmware copies payload+2..7 into the user object +0x12..0x17 [V] |
| +0x08..+0x8d | - | zero | vendor writes nothing here [V]; zero-fill choice [I] |
| +0x8e | u8 | user type: 2 = normal (1/0 only in a special locally-administered-MAC branch) | vendor `strb sl,[buf+0x9a]` [V]; firmware consumer [U] |
| +0x8f..+0xa3 | - | zero | as above |
| +0xa4 | s8 | RSSI, vendor default +100 when the BSS is not in the scan cache | vendor writes +0xB0; firmware reads the same signed byte inside the handler [V] |
| +0xa5..+0xa7 | - | zero | - |

Firmware handler CA `0x9832D` (entry 0x9832C), decoded behaviour: chip lookup from
`hdr[3]` via CA 0x961AE (requires chip+0x4B8/0x4B0 state) -> user allocate/get by the
payload u16 via CA 0x94588 (the user id space is < 0x8000; an invalid id is refused,
not dereferenced) -> fills user+0x1E from `hdr[2]`, user+0x1F from the dst nibble,
user+0x1D from `hdr[3]`, copies the MAC, sets user+0x36 = 0x0301, user+0x84 = 4 and
reads the payload RSSI byte. **No payload word is used as a pointer [V].**

Builder default: user id 0, type 2, rssi +100; the caller supplies the MAC (bench:
wlan0 address 02:00:68:69:35:01 from STATUS 3k).

### 3.2 g0 id8 - `hmac_user_add_notify_alg` (168 B payload; 180 B wire)

Vendor builder: `hmac_user_add_notify_alg` @ 0x8E624 (2.5.24; 0x8E40C in 2.4.15).

| payload off | width | field | evidence |
| ---: | ---: | --- | --- |
| +0x00 | u16 | user id | vendor writes arg1; firmware reads it first and resolves the user object [V] |
| +0x08 | u16 | alg/cfg value | vendor writes `params+0x3E0`; firmware stores it to chip+0x3E0 [V]/[U] (semantics) |
| +0x10 | 24 B | VHT capability block | vendor `mac_user_get_vht_hdl` copies 24 B from user+0x7C; firmware passes payload+0x10 to its VHT setter [V] |
| +0x28 | 44 B | HT capability block | `mac_user_get_ht_hdl`, 44 B from user+0x50; firmware setter at payload+0x28 [V] |
| +0x54 | 58 B | HE capability block | `mac_user_get_he_hdl`, 58 B from user+0x94; firmware setter at payload+0x54 [V] |
| +0x8e..+0xa4 | - | zero | not written by the vendor builder [V] |
| +0xa5 | u8 | NSS/rate byte | vendor writes `user+0xAA6`; firmware writes it to user+0x3A/0x3B/0x3C [V]/[I] |
| +0xa6..+0xa7 | - | zero | - |

Firmware handler CA `0x96225` (entry 0x96224): chip lookup from `hdr[3]`, user
resolve from the payload u16, `chip+0x3E0 = payload+0x8`, then the three capability
blocks are copied into the user object through the setter helpers; **no pointer use
[V]**. Our default sends **zero capability blocks** ([I]) which is legal data but means
"no HT/VHT/HE rates" until a real capability source is wired in (this lane does not
invent capability bits).

### 3.3 g0 id9 - `hmac_del_user_notify_dmac` (12 B payload; 24 B wire)

Vendor builder: `hmac_del_user_notify_dmac` @ 0x8D7F0 (2.5.24; 0x8D5D8 in 2.4.15).
This is the exact frame the shipped driver's `h2d_send del_user` attribute already
carries; the builder here is the same layout with the chip/vap parameters.

| payload off | width | field | evidence |
| ---: | ---: | --- | --- |
| +0x00 | u16 | user id; 0x0fff = resolve the user by MAC | vendor writes the id; firmware uses 0xfff as the by-MAC sentinel [V] |
| +0x02 | u8[6] | MAC address | vendor `memcpy_s` of 6 bytes from user+0x12; firmware `memcmp` of 6 bytes at payload+2 when the sentinel is used [V] |
| +0x08 | u8 | flag (vendor's 4th argument) | vendor write [V]; semantic [U] - builder default 0 |
| +0x09..+0x0b | - | zero | - |

Wire known-answer (by-MAC delete, chip 0/vap 0):
`000100001800090000005a5aff0f02006869350100000000`.

### 3.4 g0 id0xC - `hmac_enc_scan_send_req` (508 B payload; 520 B wire)

Vendor builder: `hmac_enc_scan_send_req` @ 0x9AD98 (2.5.24; 0x9AB58 in 2.4.15).
It allocates a 508-byte message, sets the header from the **VAP object** fields
(`hdr[1] high nibble = vap+0xFAA`, `hdr[2] = vap+0xFA9`, `hdr[3] = vap+0xFA8`),
`hdr[6] = 0x0C`, `hdr[8] = 0`, then `memcpy`s the whole 508-byte scan request built
by the cfg80211 STA path (`hmac_cfg80211_start_scan_sta` @ 0x97818) into the payload and
sends it. The scan-request layout below is the union of the vendor builder's writes and
the firmware handler's reads.

| payload off | width | field | evidence |
| ---: | ---: | --- | --- |
| +0x00 | u8 | flags: 1 | vendor STA scan builder [V] |
| +0x01 | u8 | dual-band/scan flag (vendor copies `wal+0x12C`, 1 only when both band channel lists are present) | [V] write, [I] meaning; builder 0 = single band |
| +0x02 | u8 | has-BSSID: 1 | set after the broadcast-BSSID copy [V] |
| +0x03 | u8 | number of SSIDs | vendor copies the WAL SSID count [V] |
| +0x0b | u8 | 2 or 15 (vendor: sign of `wal+0x138`; 2 = active variant) | [V] write, [I] meaning; builder 2 |
| +0x0c | u8[6] | BSSID (ff:ff:ff:ff:ff:ff for a wildcard scan) | `get_bcast_macaddr()` copy [V] |
| +0x18 | 8 x 36 B | SSID slots: bytes 0..len-1 = SSID, byte len = 0 (NUL-terminate), rest zero | vendor `memcpy_s(dest,33,ssid,len)` + explicit NUL store at slot+len [V] |
| +0x131 | u8 | scan flag byte (channel-switch scan path ORs 2 here) | [V] write, [I] meaning; builder 0 |
| +0x138 | u8 | number of SSIDs (second count copy) | [V] write; builder mirrors +0x03 |
| +0x139 | u8 | bit2 skips the scan-timeout timer registration | [V] read in `hmac_scan_proc_scan_req_event`; setter [U]; builder 0 |
| +0x13b | u8 | per-VAP scan flag; firmware handler stores it to vap+0x502 | [V] firmware read; setter [U]; builder 0 |
| +0x13c | u8 | scan-timeout mode byte read by `hmac_scan_proc_scan_req_event` | [V] read; setter [U]; builder 0 |
| +0x140 | 42 x 4 B | channel entries `{u8 num; u8 band; u8 0; u8 chan_idx}` | vendor channel-copy helper (`hmac_cfg80211_stop_sched_scan+0x5c` @ 0x96F30) [V] |
| +0x1ec | u8 | channel count (0 = whole band) | [V] |
| +0x1ee | u16 | dwell time in ms (vendor writes 20/40/60 depending on the scan variant) | [V] write, [I] condition; builder 60 |
| +0x1f0 | u8 | scan type; the firmware handler rejects the values **4 and 8** | [V] firmware check; builder 0 |
| +0x1f1 | u8 | 1 | vendor STA scan builder [V] |
| +0x1f2 | u8 | 11 (vendor STA scan type); 16 selects the doubled-dwell timeout branch | [V] write, [I] meaning; builder 11 |
| +0x1f8 | u32 | 0 | vendor builder [V] |
| +0x1fa..+0x1fb | - | zero | - |

Firmware handler CA `0x6494D` (entry 0x6494C), decoded behaviour: chip lookup from
`hdr[3]` -> **VAP lookup for id 0 only** (CA 0x581C8 with r0=0) -> if the VAP is
missing, log and return 100 (no fault) -> else store payload+0x13B to vap+0x502 and
tail-call CA 0x644A4, which validates payload+0x1F0 (4/8 rejected), checks VAP state and
copies the 508-byte payload into the VAP's scan buffer (vap+0x300). The deeper scan state
machine was not fully decoded.

**Consequence for the bench:** the scan will only produce results once a firmware VAP
object exists. Our cfg80211 M1 netdev is host-only, so the expected S1 outcome today is a
graceful refusal (no D2H scan events); the frame-validity check still works (node
consumed, no exception).

## 4. What a VAP actually needs (gap statement)

The two frames above create a **user** object in the firmware (a MAC entity with rate
capabilities). They do **not** create the per-radio **VAP** object that the scan handler
looks up. The vendor's VAP creation path is a different code chain:

* userspace `echo "Hisilicon0 create <ifname> <type> <band>" > /sys/hisys/hipriv`
  -> `wal_hipriv_add_vap` -> `wal_config_add_vap` -> `hmac_config_add_vap`
  (@0x15C95C) -> `hmac_config_add_vap_check`/`_init`/`_sync_all`, plus
  `hmac_vap_add_multi_user` (@0x15BDB0) which calls `hmac_user_add_multi_user`
  (@0x8F188) for the VAP's own users;
* the VAP object itself is configured through the g0 id1 config-event family
  (the vendor `hmac_config_send_event` builder, keys from the firmware table A/B);
  the exact key sequence for VAP create/start remains **[U]** for this lane.

Our ladder therefore sends the user half (id7/id8) and the scan probe, and records the
result; implementing the VAP object needs a follow-up RE of
`hmac_config_add_vap_init` (host) and the firmware config-key worker for it. This lane
does not guess that sequence.

## 5. Firmware-side behaviour, corrections and risk

### 5.1 Corrections register (supersedes earlier lane claims)

| earlier claim | corrected here |
| --- | --- |
| wifi-datapath REPORT: "g0 id7 user-add (0xa8) / g0 id8 alg-notify" and table row "user/VAP context: g0 id7 user-add / g0 id8 add vap" | id8 is `hmac_user_add_notify_alg` - a capability notification for an existing user, not a VAP add [V]. The VAP object is a different message family (section 4) [U]. |
| wifi-h2d-catalog Appendix B: g0 id7 "no early payload access"; g0 id8 / g0 id0xC "PTR_DEREF" | The Appendix-B window is only 0x140 bytes from the handler entry. Bounded full-function decode shows id7 reads payload+0, +2..7 and +0xA4 (RSSI) with no pointer use; id8 copies fixed capability blocks; id0xC validates and copies the whole payload. No payload word is dereferenced as a pointer in these handlers [V]. |
| wifi-h2d-catalog Appendix B: g0 id9 "no early payload access" | id9 does read payload+0 (u16 user id) and payload+2..7 (MAC, only for the 0xFFF sentinel) after the first memory compare [V]. |
| Scan request "payload 0x1FC [U]" (wifi-vendor-userspace T6) | 508 B size [V], bulk of the field offsets [V]/[I] (section 3.4); five flag bytes and the channel `idx` mapping remain [U]/[I]. |

### 5.2 Why the risk is low for id7/id8/id9

Every numeric field is either data copied into a fixed object offset or a user id passed
to the firmware's own allocator/getter, which validates it (< 0x8000) and refuses
unknown ids. The handler reaches no pointer taken from the payload. The three frames are
validated by our library against the same header rules the firmware enforces (tag, total,
group, alloc nibble, dst) and against the family payload size.

### 5.3 Why the risk is moderate for id0xC

The handler itself validates payload+0x1F0 and copies the struct, but the deeper scan
state machine (band/channel logic, IE parsing from a later exchange) was not decoded.
A malformed scan request is expected to be refused or to scan oddly, not to fault; but
this is [I], and the ladder treats S1 as the narrowest first probe and stops on any
exception.

### 5.4 Bench-visible safety rails (unchanged project rules)

Never write CA 0x400392F0 (out[5]); never post mailbox id 5 (firmware BUG trap); never
send group 1/4 H2D frames (no receive table); one frame per idea; stop on the first
exception mask; no device-RAM writes. The ladder JSON encodes these as global stop rules.

## 7. Implementation and verification

### 7.1 Code

* `vapscan_frames.c/h` - pure C99, no libc dependency, no kernel dependency in the host
  build, `__KERNEL__` include switch for module use. Builders:
  `vs_build_user_add`, `vs_build_user_alg`, `vs_build_user_del`,
  `vs_build_scan_req`; validator/decoder `vs_frame_validate`/`vs_frame_decode`;
  carrier helpers `vs_sr_node_encode`/`vs_sr_producer_next`; defaults helpers.
* The library refuses at build time: user ids >= 0x8000, the 0x0FFF sentinel on add/alg,
  scan type 4/8, > 8 SSIDs, > 42 channels, SSIDs > 32 B, non-0/1 bands, dst > 0xF;
  and at validation time: bad tag, zero/mismatched total, wrong alloc nibble, dst field
  mismatch, group without an H2D table, unknown id, id/payload-size disagreement.

### 7.2 Host verification (run 2026-11-25, host-only)

```

== selftest ==

== emit bench frames ==

```

refusal matrix, validator/decode disagreement cases, export bounds, and the SR
node/packed-producer arithmetic. Exits nonzero on the first failure.

### 7.4 Integration contract for the cfg80211/scan-ap lane

Kernel-agnostic; the planned ops callback table can call these directly:

```c
int vs_build_user_add(struct vs_frame *f, const struct vs_user_add *p);
int vs_build_user_alg(struct vs_frame *f, const struct vs_user_alg *p);
int vs_build_user_del(struct vs_frame *f, u16 user_id, const u8 mac[6],
                      u8 chip_id, u8 vap_id, u8 flag);
int vs_build_scan_req(struct vs_frame *f, const struct vs_scan_params *p);
```

`struct vs_frame { u8 buf[VS_MAX_FRAME]; u16 len; }` is the wire frame;
`vs_frame_export()` copies it to the caller's SR buffer; the driver keeps ownership of
the carrier/announce. Defaults are provided by `vs_user_add_defaults` /
`vs_user_alg_defaults` / `vs_scan_defaults`, so a driver only fills user id, MAC,
chip/vap ids and (optionally) SSIDs/channels. D2H scan events are NOT decoded by this
library (section 6; the scan/AP lane owns that decode).

## 8. Bench ladder

### 8.1 Host-tooling prerequisite

The current clean driver's `h2d_send` grammar (wifi-h2d-send) already carries
`del_user user=U [addr=8hex] [dst=N]` but not user-add/alg/scan. Before this ladder can
run, one of these must land (outside this lane's scope):

1. extend the driver's `h2d_send` grammar with `user_add`, `user_alg`, `scan_req`
   attributes that call the library and commit the node through the existing one-frame
   path (preferred; the driver already owns the gate order and budget), or
2. a bench-tooling path that injects the generated frames of recipes/frames.md through a
   validated SR post (the existing h2d-inject/hcc-service helpers).

All four frames fit the existing carrier rules (total <= 0x680, one SR node, announce id
3); the 520-byte scan frame needs its 520-byte buffer inside a node of length 520 (the
driver's node-length rule = declared total is correct for these new frames, unlike the
72-byte TXQ-sync capture oddity).

### 8.2 Ladder steps (data form: recipes/vap_scan_ladder.json)

| step | frame | total | expected |
| --- | --- | ---: | --- |
| V1 | user add, uid 0, MAC 02:00:68:69:35:01, chip 0, vap 0, type 2, rssi 100 | 180 | consumed, out[0]=0, mask 0, page/state golden, h2d ok+1 |
| V2 | user add notify alg, uid 0, zero capability blocks | 180 | same |
| V3 | read-only check (no frame) | - | mask 0; h2d ok = 5; page/state golden |
| S1 | scan request, whole band, no SSID, dwell 60, type 0 | 520 | consumed, mask 0; either a graceful no-VAP refusal or g1 15/16/17 events |
| S2 | scan request, 2.4 GHz ch1-13 (`idx = chan-1` is the [I] item) | 520 | same as S1; only after S1 PASS |
| V4 | user delete by MAC (0x0fff sentinel) | 24 | consumed, mask 0; leaves no user object |

Run order: C1 calibration boot (existing ladder: golden boot -> ready -> ctx_create type
1 -> txq_sync72 -> cfg_cal 3507) then V1, V2, V3, S1, S2 (optional), V4. The driver's
one-frame budget is 8; C1 used 3, so V1-V2-S1-V4 fit (7) and S2 makes 8 (full budget) -
S2 is optional for exactly that reason.

### 8.3 Stop rules (any one aborts the lap; no retry in the same boot)

* exception mask CA 0x40008 != 0, or an exception-staging frame appears;
* the boot page 0x86807FEF/7/2/0xABCD or core state 1 changes, or g+0xB4/+0xB8 != 0;
* the SR node is not consumed within the bounded poll window (H2D timeout);
* h2d_status refused increments;
* any dmesg fault/abort line.

On stop: record mask / out[] / rd_catalog / dmesg, power-cycle, and analyse offline. Never
re-send the failed frame, never write out[5], never use mailbox id 5, never send group 1/4.

## 11. Limits and publication boundary

* **Host-only.** Nothing here was validated on the bench router; the frames are
  compile-verified and hand-checked against the vendor builder/firmware handler decode,
  not device-verified. The D2H expectations are from the vendor host code, not from our
  captures.
* The vendor module addresses and firmware handler offsets are **derived facts**; no
  vendor code, object bytes, firmware bytes, calibration values or secrets are committed.
* The scan payload is structurally decoded but not byte-complete; the builder is
  deliberately conservative (whole-band, no SSID, no channels by default) and the [I]
  fields are labelled in the code and here.
* The PD4-patched firmware remains a research artifact; this lane does not change it and
  its frames are equally valid on a vendor-firmware golden boot (they are ordinary
  post-ready H2D messages).
