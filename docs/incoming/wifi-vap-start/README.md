## TL;DR

1. The vendor's real **VAP create/start path is WAL group-2 cfg events**, not g0: `wal_hipriv_add_vap`
   -> `wal_send_cfg_event` cmd **0x0064** (body 24 B) and `wal_start_vap` cmd **0x0065** (body 12 B);
   the AP-config event is cmd **0x0127** (body 156 B, still gap G1).
2. The **g0 id1 config-event family** carries the hmac/mac-layer VAP add (key **0x0064**, module
   context create helper CA 0xFE6BC) and VAP start (key **0x0065**, worker CA 0x46394, 12-byte body).
3. The **start_sta pair is byte-decoded**: g0 id **0x0010** (16 B) and g0 id **0x000F** (64 B).
4. The 2026-11-26 no-scan-result is explained by the scan handler's first gate: module(hdr[3])+0x4B8
   must be non-NULL; the C2 ladder created module 4, while user/scan frames select module 0 - so the
   handler returned 100 before touching the payload. The ladder posts a module-0 VAP add first.
5. All frames are synthesized (not vendor captures); stop rules and a read-only readback pack make
   the hardware step falsifiable.
