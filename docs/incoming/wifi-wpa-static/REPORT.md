# wifi-wpa-static - WPA2 key path static RE + cfg80211 M3 ops

**Lane:** wifi-wpa-static (shared task task-139), **host-only**, 2026-11-28.
**Scope:** reverse the vendor key-install path, implement the cfg80211 M3 key
ops with a decoded firmware message builder behind a fail-closed parameter,
compile-verify on the hardware-fired final combined tree, host-test the wire
builders, and design (not fire) the attended bench ladder.

**No device was touched in this lane. No vendor binary/firmware/calibration
byte is committed.** All derived addresses/offsets are in
[TABLES.md](TABLES.md); local vendor modules and the firmware image stay
local/gitignored as project policy requires.

---

## 0. TL;DR (ten answers)

1. **The cfg80211 key ops ARE implemented by the vendor driver** - the ops
   map from wifi-driver-re (fields 6-10: add_key 0x1007f4, get_key 0x100b44,
   del_key 0x100d98, set_default_key 0x100ffc, set_default_mgmt_key 0x101198
   in the 2.4.15 module) is complete, and each op sends **one decoded
   firmware config event**; there is no host-side MAC-register sequence for
   keys.  The 2.5.24 shipped module is the same instruction stream at +0x208
   (add_key identical 848 B), so this RE covers both driver replicas.
2. The wire carrier is the **group-0 id-1 config event** (12-byte HCC header,
   token[8], u16 cmd, u16 len, body, 4 pad bytes, tag 0x5a5a) - the same
   bench-proven family as the AP-start and TXQ-sync frames [V*].
3. Command ids [V]: add_key **0x0078** (body **0x44**), set_default_key
   **0x0079** (body **0x28**), del_key **0x007A** (body **8**).  The firmware
   static table A (CA 0x10C23C) routes them to workers **CA 0x0A5825 /
   0x0A5C9D / 0x0A4271**.
4. The add-key body layout is fully decoded (TABLES T3): key_index, pairwise,
   MAC[6], key[32], seq[16], key_len(u32 @0x38), seq_len(u32 @0x3c),
   cipher(u32 @0x40).  Independent cross-check: the vendor's own
   `hmac_user_key_to_key_params` builds the identical layout from its
   in-driver per-user key slot.
5. **Cipher mapping is decoded and exact**: the firmware uses the low byte of
   the cfg80211 WLAN_CIPHER_SUITE_* value as its enum, with three classes
   (data 0x0714 / mgmt 0x3840 / WEP 0x0022) and index rules (data <=3, mgmt
   4..5).  The lane refuses unknown ciphers with -EOPNOTSUPP rather than
   guessing.
6. **hostapd WPA2-AP startup installs the GTK without any client**: after
   NEW_BEACON -> AP-ENABLED, `wpa_init_keys()` sends NEW_KEY (group,
   key_idx=1, CCMP, 16 B) and SET_KEY (default multicast, idx=1).  This is
   exactly the M3 blocker reported by wifi-image-polish - no RX/association
   is needed for it.  So clearing this path makes a WPA2 AP *security setup*
   complete; the 4-way handshake itself still needs the RX path.
7. **Implemented on the final combined tree**: `.add_key`, `.del_key`,
   `.set_default_key` (cfg80211 WARN requires all three together), the
   3-message portable builder library, provider caps/callbacks, portable
   op-map update, and a sysfs status line.  Everything is gated by
   **wpa_keys=0 fail-closed default** plus the existing allow_frames/post
   gates; key material is never logged.
8. **Compile-verified on the hardware-fired tree**: the build gate first
   re-stages the committed final combined chain and reproduces the pinned
   fired identity **269,688 B sha256 b5dfb883a035...** (CHAIN-ID-OK), then
   applies this lane's patch on top and builds warning-free.
9. **Host tests**: `tools/key_selftest.c` exercises cipher classification,
   all three body layouts, all three g0 frames (header/tag/cmd/len/pad),
   bounds and refuse rules; **all checks pass** (see evidence).
10. **Honest remaining blockers**: the full WPA2 association/4-way handshake
    needs the RX path (0 captures today) and mgmt RX/EAPOL; a pairwise PTK
    add_key will be posted but the firmware refuses an unknown STA MAC until
    firmware STA users exist (`.add_station`/mgmt RX).  STA
    `.connect`/`.disconnect` need the join payload that is still [U]; they
    stay clean -EOPNOTSUPP stubs (section 8).

## 1. Method and local artifacts

Host-only static analysis: ARM disassembly of the two shipped vendor host
modules (pyelftools relocation resolution + capstone ARM/Thumb), firmware
Thumb disassembly at firmware-CPU addresses (file offset + 0x40000), and the
committed project docs (wifi-driver-re, wifi-datapath, wifi-h2d-catalog,
wifi-ap-start, wifi-image-polish).  The firmware image and vendor modules are
local, gitignored evidence (see TABLES header); only derived
addresses/offsets/constants appear in this tree.  Cross-checks used:

* the cfg80211 ops table (wifi-driver-re) gives the five key callbacks;
* the g0 id-1 worker table generated by wifi-datapath
  (`tables/firmware-config-keys.md`) gives keys 0x78/0x79/0x7A and their
  worker CAs;
* the vendor host sender disassembly gives the per-op body construction;
* the firmware worker disassembly gives the consumer-side field offsets,
  bounds and cipher classes;
* the 2.5.24 vs 2.4.15 comparison shows identical code for the key ops.

## 2. The vendor cfg80211 ops (what they do, exact sequence)

`wal_cfg80211_add_key` (2.4.15 0x1007f4, 848 B): validates
key_len <= 0x20 and seq_len <= 0x10, builds the 0x44-byte body (TABLES T3)
from `struct key_params` (key/seq pointers, lengths, cipher), then sends
`wal_send_cfg_event(netdev, group=1, len=0x48, data={0x0078,0x44,body})`
and waits for the firmware config-sync response.  `wal_cfg80211_remove_key`
sends cmd 0x007A with an 8-byte body; `wal_cfg80211_set_default_key` sends
cmd 0x0079 with a 0x28-byte body (key_index/unicast/multicast);
`wal_cfg80211_set_default_mgmt_key` reuses cmd 0x0079 with a class flag;
`wal_cfg80211_get_key` sends its own query event (reply layout [U], not
needed for WPA2-PSK).  Full offsets and instruction-level clues: TABLES T1.

The **same firmware command** is also built by the vendor HMAC layer:
`hmac_user_add_key` (0x1638) -> `hdpp_config_send_event` (0x59c0) with
cmd 0x0078/len 0x44, and `hmac_enc_11i_default_key_msg` (0xa3c9c) ->
`hmac_config_send_event` with cmd 0x79 [V].  That is important for the
clean-room driver: the g0 id-1 carrier is not a guess - the vendor host itself
emits this exact frame on its HMAC path, and the project bench already
executed the same family for AP start.

## 3. The firmware side (workers, bounds, where the key lands)

Table A rows 0x78/0x79/0x7A dispatch to workers CA 0x0A5825 / 0x0A5C9D /
0x0A4271 (firmware CPU addresses; TABLES T2).  The add-key worker:

* reads key_index (<=5), pairwise, MAC, key_len (<=0x20), seq_len (<=0x10),
  cipher (low byte) from the body exactly as decoded in TABLES T3;
* for pairwise keys looks the user up by MAC (0x1028f4 / 0xbd430); for group
  keys uses the VAP user id at `module_ctx+0xacc`; validates the user
  (0xd6a1e);
* classifies the cipher (TABLES T5), enforces the data/mgmt key-index split
  (data <=3, mgmt 4..5), stores cipher/key index in `user+0x310/0x311`
  (data) or `user+0x312/0x313` (mgmt), and installs the key cache entry via
  the key-table manager at `module_ctx+0x4b8` (0xa43e8);
* copies key[32]/seq[16] from the body straight into the cache; there is no
  host-visible MAC/register programming step.

The default-key worker's data path is a no-op success for non-WEP keys (the
WEP legacy branch is gated by 0xfff6c), so a WPA2 CCMP group-key selection
event is consumed safely.  The mgmt path additionally wants a cipher byte at
body+0x04 that the vendor builder does not fill (TABLES T4) - one reason this
lane leaves `set_default_mgmt_key` unregistered.

## 4. hostapd needs and what this driver now does

TABLES T7 traces the hostapd v2.12 source used by the project image:
`hostapd_setup_interface()` runs NEW_BEACON (`.start_ap`) and then
`wpa_init_keys()`; the group state machine enters SETKEYSDONE and installs
the GTK with

* NL80211_CMD_NEW_KEY: group key, key_idx=1, cipher CCMP (0x000fac04),
  key_len 16, no MAC -> cfg80211 `rdev_add_key(pairwise=false, mac=NULL)`;
* NL80211_CMD_SET_KEY: default + multicast -> `rdev_set_default_key(1,
  unicast=false, multicast=true)`.

Per-STA PTK install (after M4) is NL80211_CMD_NEW_KEY pairwise with the peer
MAC; deletion is NL80211_CMD_DEL_KEY.  The driver now implements all three
callbacks (cfg80211 6.18.60 core.c line 530 requires add_key with del_key and
set_default_key together, or it WARNs at wiphy registration).

## 5. Implementation (this lane's patch)

Patch: [patches/0001-wpa-static.patch](patches/0001-wpa-static.patch) applies
on top of the final combined hardened tree (base 242572/44c6cc12 ->
polished -> dp-tuning -> scan-tuning R4 -> stability hardening).  New files
are also reproduced under [src/](src/) for review:

| file | role |
| --- | --- |
| `src/hi5622_key_frames.h/.c` | portable C99 builders: 3 bodies + 3 g0 id1 frames + validation/refuse rules |
| `src/hi5622_keys.c/.h` | kernel cfg80211 layer: M3 ops, wpa_keys/wpa_key_module params, gates, status |
| patch hunks | `hi5622_frames_api.h` (3 caps + neutral params + callbacks), `hi5622_scan_logic.c` (cap pairing validation), `hi5622_vapscan_provider.c` (callbacks + cap registration), `hi5622_cfg80211_ops.c` (`.add_key/.del_key/.set_default_key`), `hi5622_cfg80211_logic.c` (portable op map rows), `hi5622_cfg80211.c` (status line), Kbuild |

Policy and safety:

* **wpa_keys=0 is the compiled default**: every key op returns -EOPNOTSUPP
  before a frame is built.  The bench ladder sets wpa_keys=1 together with a
  finite `allow_frames` budget;
* `wpa_key_module` selects the g0 header module/VAP index (default 0, the
  same module the bench-proven AP-start frames used);
* all three ops require a committed AP start on this module load (the
  firmware group-key path installs against the running VAP; hostapd's order is
  start_ap -> AP-ENABLED -> wpa_init_keys);
* keys are posted through the existing fail-closed `hi5622_frame_post()`
  gate (armed/released/phase/out[0]/gap/budget, one attempt, no retry);
* key material is copied only into the wire frame; dmesg/log/status carry
  index/cipher-class/length metadata only, never key bytes;
* unknown cipher low bytes -> -EOPNOTSUPP; out-of-range indices/lengths ->
  -EINVAL before a frame exists.

## 7. Bench ladder design (not fired here)

[LADDER.md](LADDER.md) and [ladders/wpa2-ap.json](ladders/wpa2-ap.json) define
rungs R0-R4: R0 golden-boot control with the open-AP fixture, R1 fail-closed
proof (wpa_keys=0 + WPA2 hostapd -> key op refused, no frame posted), R2 the
primary WPA2 GTK rung (wpa_keys=1, expect `key_add` then `key_default`
dmesg lines, no exception), R3 blocked-by-RX pairwise rung (documented as a
future M4 gate), R4 soak/teardown observation.  Every rung requires the
golden page/mask check and an attended recovery door; the lane fires nothing.

## 8. Feasibility of `.connect`/`.disconnect` (STA) - verdict: not this lane

The vendor `wal_cfg80211_connect` (2.4.15 0x100388 / 2.5.24 0x100590)
builds a WAL join request from `cfg80211_connect_params` and waits for a
firmware connect/asoc response; the join payload family (g0 id0xF
`hmac_sta_sync_join_req_params`, plus g0 id0x10/0x12/0x13 and g2 id3/5
events) is recorded as [U] in the datapath catalogue - it is not decoded
enough to build a non-speculative message.  Completion also needs management
RX (beacon/probe/assoc) and the RX data path, which are the project's known
remaining blockers (0 RX captures).  Implementing a `.connect` that posts an
undecoded frame would violate the lane's "never fake success" rule, so the
stubs stay -EOPNOTSUPP; the RE pointers above are the starting material for a
future STA lane.

## 9. Limits and evidence markers

* The firmware worker behaviour is static disassembly [V]; no key was
  installed on hardware in this lane.  The g0 id-1 carrier is [V*] (bench
  executed for AP start/TXQ sync), not [V*] for the key commands themselves -
  rung R2 is what turns that into a hardware fact.
* The 2.4.15 and 2.5.24 host modules were compared for the key ops only (same
  code at +0x208).  The PD4 firmware is the vendor-derived research image; the
  firmware table A rows were cross-checked against the committed generated
  table, not re-generated here.
* get_key's reply layout and the mgmt-key path are [U]/[I] and deliberately
  unimplemented.
* The patched artifact has **not been fired**; wpa_keys defaults to the
  fail-closed value and the shipped behaviour without wpa_keys=1 is exactly
  the previous module plus the new (inactive) ops and status text.
