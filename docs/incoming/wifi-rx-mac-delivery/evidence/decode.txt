B. D2H source selection (why the firmware's own frames deliver and client frames do not)
  The D2H ring is a single firmware->host HCC message channel.  Every firmware-originated
  message that reaches the host (ready pair g4 id1/id2, config replies g1 id3, HEARTBEAT
  g4 id4) and the management-RX event (g1 id13) all deposit through the SAME primitive
  (hcc_msg_tx 0x102760 -> ETE node 0xC192A -> notify 0xC6170).  There is no per-id ring
  and no host-side gate that could selectively hide g1 id13.
  => the bench fact 'the firmware's own frames deliver' proves only that the deposit,
     notify and host-consume paths work.  It does NOT prove the MAC-RX intake ran.

C. the intake that is missing
  Client frames must become an HCC message node consumed by the RX descriptor handler
  (pop at 0xBA0C0 -> bl 0xB9780 at 0xBA48A).  The producer of those nodes is the SMAC RX
  completion path (MAC PPDU -> firmware RX descriptor -> node).  That producer entry is
  [U] in this image (the ISR names table is not code-referenced; see TABLES T7).
  The demand-side state that the consumer itself reads is the per-chip RX ctx at
  chip+0x1a00 (0xB97EE); a NULL there drops the frame with log 0xA4E after intake.
