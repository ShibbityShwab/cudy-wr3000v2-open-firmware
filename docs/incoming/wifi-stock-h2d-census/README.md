# wifi-stock-h2d-census - the stock pair-A H2D capture: corrected census, the g12 answer, the new families

**Lane:** wifi-stock-h2d-census (shared task-232). Host-only analysis; no bench contact.
**Status:** decode complete. This lane answers the family census, the "g12" question, the new
families, and the 5 GHz beacon-candidate question raised by the first stock H2D capture.

## Input

The first-ever **stock** (pair-A vendor boot) H2D sampler log, local only (vendor-derived DRAM
content, **not committed**):

* path `/tmp/h2d-stock.log`; 335,359 B; sha256 `423ebf26...e83c186b` (full value in
  [evidence/LOG-SHA256.txt](evidence/LOG-SHA256.txt)); local copy under
  `build/wifi-stock-h2d-census/h2d-stock.log` (gitignored);
* 1129 M records, span 86.5 s (ts 68391..154909 ms), ETE channel 0 only; ch1/ch2 idle;
* header: `# omo_h2dsampler v2 ts0=68391 window=0x583f2000 module=hi5622v100_plat
  duration=90 period_ms=10 access=mmap` - a **v2** sampler build (mmap window, 10 ms
  period) whose source is not committed; the record format is v1-compatible. The v2 flags field
  reads 0x0000 on all 1129 records - see REPORT sec. 6 caveat C3 before drawing any driver
  conclusion from it.

## Headline results (all [V] unless graded otherwise)

1. **The raw census over-counts by 3.4x.** Only 332/1129 records are length-valid H2D sends
   (node len == frame total + tag); 4 are stale-head aliases; 793 are torn reads (stale node
   descriptor / recycled buffer / sampler re-walk). The corrected census is in TABLES sec. 1.
2. **There is no "g12 family".** The 7 g12 id29 records are the already-known 16-B HCC-timer
   message (hcc_timer_timeout_proc, group 2 id 0x1d, 4-B host-pointer payload) read with a
   torn/stale header (0c 18 30 00 instead of the canonical 02 01 00 00; 381/382 of the same
   class carry the canonical head). The 4 g12 id1 records are stale-head aliases of two real
   config events: g0 id1 key 0x00d8 (48 B) and g0 id1 key 0x0127 set_beacon (184 B, 3 records;
   one is byte-identical after the 4 stale head bytes).
3. **The 01:80:c2:00:00:13 / 0x893a Ethernet frame is not a message.** It is an **IEEE 1905.1
   (Multi-AP / EasyMesh) Ethernet header fragment** that lives in adjacent host DRAM and is
   exposed only because the stale node length makes the sampler read past the 16-byte message
   buffer (171 records carry the fragment; 56 B over-read on the 72-B reads). It is evidence of
   1905.1 control traffic in the stock image, **not** an H2D per-VAP data channel.
4. **Four new length-valid H2D families are decoded with builder evidence:** g0 id22
   hmac_chan_do_sync (a 5 GHz ch 36 channel sync), g0 id32 hmac_config_h2d_send_app_ie,
   g0 id36 hmac_scan_config_bss_color, plus the already-known g0 id2 alg request and g0 id12
   scan request (here: a 5 GHz channel list).
5. **5 GHz beacon candidate: none on H2D.** The stock is a 5 GHz-active boot (5 GHz channel 36
   sync + 5 GHz scan list + set_beacon posts), yet no H2D family between the last beacon-template
   post and the beacon TX is a beacon/TBTT arm. This confirms the committed wifi-5g-tx-scheduler
   result: the 0x40101220 gate is firmware-internal. Do **not** fire the g12/timer records - see
   FIRE-RECIPE.md.

## Reproduce

```sh
python3 tools/decode_stock_census.py --selftest
python3 tools/decode_stock_census.py --input /tmp/h2d-stock.log > evidence/CENSUS.txt
python3 tools/decode_stock_census.py --input /tmp/h2d-stock.log --aliases > evidence/ALIASES.txt
python3 tools/decode_stock_census.py --input /tmp/h2d-stock.log --family 0 22 --torn
```

Sibling committed lanes this builds on: wifi-rx-h2d-trace (wire formats + decode_h2d.py),
wifi-f1-from-capture (family tables + the torn/alias rule), wifi-rx-h2d-window (sampler),
wifi-5g-tx-scheduler (the 0x40101220 beacon gate), wifi-h2d-catalog (firmware receive tables).

## Redaction

Quoted frames are **decoded protocol bytes as text** (policy allows). Per-unit MAC addresses are
replaced by documentation examples (d4:0d:ab:XX:XX:XX); host pointer values are quoted as decoded
protocol bytes only. The capture log itself is vendor-derived DRAM content and stays
local/gitignored. No vendor binary, firmware byte or secret is committed.
