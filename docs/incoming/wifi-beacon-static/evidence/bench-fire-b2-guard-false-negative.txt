## Verdict — false negative in the lane's fail-closed guard

The readback gate was wrong, not the sequence: the stability lane's final
combined module (b5dfb883) also reads module_ctx+0x190 == 0 after 100 ms on a
SUCCESSFUL AP start (its fresh-path exemption is exactly why it works).  The
field is populated asynchronously / may not be the VAP-validity indicator this
lane assumed, so a fresh base post must not be refused on it.

## Fix (this build)

* beacon_static path no longer posts user_add when the latch pre-existed this
  call (or on a host-side stop restart): it logs and continues.
* The bounded readback is now LOG-ONLY for a fresh base post
  ("...readback=... (fresh base post, non-gating) - continuing the vendor
  order").  A genuinely stale PRE-EXISTING latch still fails closed with
  "a pre-existing VAP base latch reads module_ctx+0x190 == 0 ... power-cycle"
  (same rule as the stability patch).
* Re-fire expectation unchanged: vap_add -> channel 0x0124 -> ap_ssid ->
  ap_cfg -> VAP start, hostapd AP-ENABLED, channel readback line, page golden.
