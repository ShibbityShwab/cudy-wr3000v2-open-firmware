# REPORT - first MAC data-plane TX/RX (wifi-dp-txrx, task-122)

**Lane:** wifi-dp-txrx (shared task task-122), host-only, 2026-11-26.
**Status:** implementation + host tests + compile-verified kernel extension +
validated bench sequence. **Not fired at the device.** No completed TX/RX frame
has been observed yet; this lane defines and implements the first attempt and
the exact observables that decide it.
**Base:** wifi-datapath-bringup (task-111) E1 PASS: dp_probe/dp_setup/dp_rings
+ TXQ-table address sync g0 id1 key 0x0320 (module 462,952 B sha 8fc693ad...,
37/37 automation checks). This lane's patched build is 540,936 B sha
aae8487b... (base + this lane's two new objects), same E1 actions, 0 warnings.

## 0. TL;DR - what is new here

1. **The TX publish path is decoded and implemented.** The 12-byte device-RAM
   MSDU-info table entry is not just {ring_devva,0,0}: dword1 is the packed
   producer index the host publishes after the ring entry is visible
   (hmac_tx_msdu_ring_push), and dword2 is the device-consumed index the host
   reads back (hmac_tx_msdu_ring_proc). The E1 lane had left dwords 1/2 "[U]".
2. **The TX completion check is now concrete** without decoding tx_ba_info:
   read table dword2 and compare it with the published dword1; a consumed entry
   is additionally marked ctl byte 7 | 0xE0 by the host consumer. This is
   implemented as dp_tx_status (completion_pending, table image) and posted
   before the first bench frame.
3. **The first frames are built**: 802.11 probe request / null-data / QoS-null /
   ARP-data MPDUs, 8-byte entries with the vendor ctl bit layout, and a
   coherent frame buffer laid out as the vendor builds it (host word + 16-byte
   zero DMA header + MPDU) - the 20-byte descriptor and the
   data-0x14 -> data-0x10 transform are pinned from the vendor code.
4. **An RX capture path exists** that is safe by construction: one bounded
   2000 ms poll of the MAC completion producer (+0x4c), then a scan of all
   768 host-DRAM RX buffers for the 0x28-byte device descriptor. It moves no
   ring pointer and reposts nothing, because the completion-word format is
   still [U]. Consume/repost arithmetic is implemented and host-tested, but
   gated on a decoded completion format (bench evidence first).
5. **Kernel integration is minimal**: one small patch to the E1 lane
   (bind at end of dp_setup, release calls, four attributes in the existing dp
   group, two Kbuild objects); all TX/RX logic is in this lane's files. The
   patch is generated by tools/patch_builder.py and the build fails on drift.

## 1. What was decoded (the facts the implementation needs)

### 1.1 Device-RAM table entry = {ring devva, published wptr, device rptr} [V]

`shuangta_tx_msdu_ring_buf_alloc` (wifi.ko 2.4.15 0x38f5c) allocates the
host ring with `oal_noncache_alloc`, initialises the per-(user,tid) slot
(ring host ptr +0x40, table-entry host VA +0x44, ring DMA +0x48, ring index
+0x4c/+0x50) and writes the 12-byte device-RAM table entry:
`{pcie_if_hostca_to_devva(ring), 0, 0}`. `hmac_tx_msdu_ring_push` (0x18f18)
then, for a queued frame: writes `{buf_devva, ctl}` into the ring slot,
`dmb ish`, computes the next packed index (index+1; on depth 64 wrap index=0
and toggle phase bit 15) and publishes it **into table entry +4** (band 0
path), then mirrors it into the host shadow. `hmac_tx_msdu_ring_proc`
(0x1cab4) reads the device-consumed index from **table entry +8**, checks the
pair with `hmac_tx_msdu_ring_rw_index_check`, and walks entries up to the
published index, marking each processed entry's ctl byte 7 with 0xE0
(`shuangta_tx_msdu_info_ring_magic_set`). Static assertions for all of this
are in tools/dp_txrx_static_decode.py (87/87).

### 1.2 Ring entry ctl layout [V]

`hmac_tx_msdu_ring_push` builds buf_devva = hostca(buf) + 0xC0600000 then
pcie_if_hostca_to_devva; the low 12 bits of ctl are skb->len;
`hmac_tx_frame_control_dscr_set` (0x18b9c) writes ctl byte 2 bits 4/5 to
0x10/0x20/0x30 (vap type 1/2/3) after clearing 0x30, based on the vendor's own
frame class; tid/path/header bits are set from the skb/tx header in the vendor
and are fixed for this lane (tid 0, path 0, header flag 1 for mgmt, 0 data [I]).

### 1.3 Frame buffer layout [V]/[I]

`hmac_tx_msdu_dscr_add` (0x19b40) expands 0x14 bytes of headroom, zeroes the
20 bytes below skb->data, stores the skb pointer at data-0x14 and DMA-maps
data-0x14 .. data+len. `shuangta_get_msdu_info_ring_addr` (0x38ad8) returns
data-0x10 for the ring entry. So the device-visible buffer starts with the 16
zero bytes at data-0x10 followed by the MPDU. This lane reproduces exactly that
as one coherent buffer: [host owner u32][16 B zero DMA header][MPDU]. The
semantics of the zero header are [I]; the first bench frame is the experiment.

### 1.4 RX rings and descriptor [V]/[U]

E1 already allocated/programmed the RX rings: norm free 256 x 4 B, small free
512 x 4 B, completion 4095 x 4 B, buffers 0x63c / 0xb0 with a 4-byte host word.
The descriptor at buffer+4 is parsed from the observed field accesses of
`shuangta_host_rx_get_msdu_info_dscr` (0x3843c); only +0x1e payload_len (the
vendor's skb_put length) is used as a fail-closed acceptance test. The
completion-ring 4-byte word format remains [U] - hence capture-only.

## 2. What is implemented

### 2.1 Portable logic (src/dp_txrx.h/.c, host-tested, no Linux headers)

* table entry pack/unpack, per-(user,tid) CA/ACP arithmetic (12-byte stride,
  index tid+user*8, ACP alias +0x01000000);
* 8-byte MSDU entry encode/decode with range-checked ctl fields, processed
  magic 0xE0 check/set;
* packed-index arithmetic: pack/unpack/next/count for depths 64/256/512/4095;
* frame buffer init/check for the [owner][16B zero][MPDU] layout;
* 802.11 MPDU builders (probe request, null-data, QoS-null, ARP broadcast),
  FC -> ctl vap-type/tid/header-flag mapping;
* RX 0x28-byte descriptor parser (observed fields, fail-closed on payload_len),
  capture builder (descriptor + bounded MPDU bytes), RX state (norm/small/cmp
  packed rptrs), pending/plan/commit/free-entry helpers. Plan is explicitly
  capture-only: it never moves a pointer; commit requires the caller's decoded
  ring kind and is sequential.

### 2.2 Kernel extension (src/hi5622_dp_txrx.h/.c + patch)

| attr | mode | action |
| --- | --- | --- |
| dp_tx_frame (1..4) | WO | build the selected MPDU, write it into the one coherent frame buffer, write the 8-byte MSDU entry for user 0/TID 0 slot wptr&0x7fff, dma_wmb, publish packed next wptr into the device-RAM table entry dword1 (+ read-back of all three dwords), record last entry/table/len, log one evidence line. Budget 8 posts/load; requires E1 setup + the 0x0320 sync in this load. A read-back mismatch closes the lane (failed=1, no retry). |
| dp_tx_status | RO | bound/failed/frame_ready/posted/wptr, completion_pending (device rptr vs published wptr), MSDU table entry image, last frame + entry + table, MAC band-0 counters (+0x00/+0x38/+0x3c/+0x40/+0x48/+0x4c/+0x50/+0x54), stop rules. |
| dp_rx_poll ("1") | WO | one-shot, bounded 2000 ms read-only poll of MAC +0x4c, then a scan of all norm/small RX buffers for parseable 0x28-byte descriptors; captures raw completion word + descriptor + up to 128 MPDU bytes. Moves no ring pointer, reposts nothing. |
| dp_rx_capture | RO | the captured evidence (counters, capture count, per-capture descriptor/MPDU hex) + the [I]/[U] note. |

The patch `patches/0001-hi5622-dp-txrx.patch` adds only the include, the bind
call at the end of a successful dp_setup, the release calls, the four
device_attribute objects inside the existing dp attribute group (the 6.18
DEVICE_ATTR_RO/WO macros define attributes static, so they cannot be shared
across translation units), and the two Kbuild objects. All TX/RX logic lives in
this lane's src/ files; the E1 lane is not modified on disk.

### 2.3 The exact host sequence (as coded and as sequenced)

    boot golden -> ready pair -> ctx_create (g0 id1 key 0x64)
      -> dp_probe  (ONE read-only MAC band-0 word)
      -> dp_setup  (E1: TXQ table + rings + table entries + 14 MAC regs)
      -> dp_txq_sync (g0 id1 key 0x0320; gate for frames)
      -> dp_tx_frame 1 / 2 / 3   (probe req, null-data, QoS-null)
           entry -> dma_wmb -> table dword1 publish -> read-back dwords
      -> dp_tx_status             (completion_pending, table image)
      -> dp_rx_poll "1"           (read-only completion/descriptor capture)
      -> dp_rx_capture            (evidence)
      -> post packs: mask/staging 0, page/state golden, out[0]/out[2] 0

The sequence file is sequences/ladder-f-txrx.json (21 steps, 205 rendered
lines); it is validated through the bench tooling validator in memory
(12/12 checks) because the four new attribute names need a one-line allowlist
handoff (tools/validate_sequence.py prints it).

## 3. Expected bench observables (see BENCH-LADDER.md)

| step | PASS observable | non-PASS / stop |
| --- | --- | --- |
| dp_tx_frame 1 | dp_tx_status posted=1, ring_index=0, last entry bytes + table image {ring, 0x0001, rptr} | table read-back mismatch -> lane closed; no retry |
| TX completion | completion_pending=0 (device wrote table dword2 = published wptr) | pending stays 1 -> POST-ONLY (rings accepted, MAC did not consume) - not a crash, record and go to the VAP-precondition step |
| dp_rx_poll | polled=1 + counters captured (cmp wptr delta, norm/small rptr) | no completion within 2 s -> NO-RX recorded; not a failure |
| dp_rx_capture | captures>0 with desc_ok and a plausible 802.11 FC byte (0x80/0x40/0x08...) | 0 captures -> RX path unproven, keep [U] |
| post packs | mask 0, staging 0, state 1, page 0x86807FEF, out[0]/out[2] 0 | any deviation -> stop the boot, power-cycle |

The TX *air* side needs the firmware's VAP/user object to be started: the
project's working chain now creates it through the mode-1 VAP ladder
(vap_add g0 id1 key 0x64 + vap_start g0 id1 key 0x65 consumed, provider module
738,112 B sha e09dc697...). That is a different module build from this E1+txrx
module, so ladder F has two modes documented:

* **F-POST (this module):** proves the host->ring->table->device path and the
  completion read-back; no VAP is started, so the MAC may not transmit.
* **F-AIR (follow-up merge):** merge this lane's two objects into the
  scan-ap/vap-start provider module (same base tree) so the mode-1 VAP create
  and the TX post run in one load; then the same dp_tx_frame actions can
  produce an actual on-air frame. The merge is a Kbuild/source-merge task for
  the integration lane; nothing in this lane's logic depends on it.

## 4. [U] / risks (honest list)

1. **TX completion semantics on the device side**: table dword2 is the vendor
   host's read-back source [V], but this is the first time a clean-room host
   publishes a wptr; the device may require additional hdpp/EDCA/VAP state
   before its MAC engine consumes the ring (likely; mode-1 VAP create is the
   known precondition for firmware scan). The ladder therefore distinguishes
   POST-ONLY from COMPLETED.
2. **The 16-byte zero DMA header**: content is literally what the vendor
   zeroes [V], but its device-side meaning is [I]. If the first frame is not
   consumed, a controlled next experiment is the vendor's other observed
   layout (data-0x14 as the entry devva) - one idea per boot, documented in
   BENCH-LADDER decision matrix.
3. **ctl vap type 1/2/3 mapping** is extracted from the vendor's descriptor
   writer but the selector is the vendor's internal frame class [I]. Ladder
   posts mgmt=1 and data=2 variants so the device-side response discriminates.
4. **RX completion word format [U]**: capture-only; consume/repost is coded
   and unit-tested but not enabled. No pointer is moved before the format is
   decoded from a bench capture.
5. **RX frames may not arrive at all** until a VAP is started and the radio is
   on the right channel; the scan results path (g1 id15/17) is a firmware
   event path, not the MAC-into-host-buffer path. A zero-capture outcome is
   reported as NO-RX, not FAIL.
6. **Band 1 is not programmed** (same as E1). No MAC write outside band 0.
7. No msleep/IRQ dependency: the driver polls; no IRQ line is assumed (the
   project has no MSI/INTx demux).
8. The ARP-data builder uses documentation IP addresses and the project's
   example MAC; never a per-unit value.
