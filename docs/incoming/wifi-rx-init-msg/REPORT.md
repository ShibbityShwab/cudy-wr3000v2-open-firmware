**Lane:** `rx-init-decode` (shared task **task-170**), 2026-11-26. **Host-only**: static analysis
of local artifacts; no device contact, no write to any vendor artifact, no vendor bytes committed.
**Companions:** [README.md](README.md), [FIRE-RECIPE.md](FIRE-RECIPE.md),

## 0. One-line verdict and what it means for the open RX bug

The vendor's **boot/init call chain sends no host-to-device message at all** - `hmac_main_init ->
hdpp_main_init -> hdpp_chip_init/hdpp_var_init` is registration/resource init only [V]. Every
vendor g0-id1 config event comes from a runtime/WAL/ops path. The firmware's config-key dispatch
table has **8 live keys**; the vendor module's 244 config-event keys cover **7 of them**; the eighth,
**key `0x0004`**, has **no sender anywhere in the shipped module** [V]. Its firmware worker
(CA `0x811CD`) is a **safe single-byte write into the created context block**
(`ctx[+0x190][0x52] = data[0]`, with a clean refusal if the context is absent) [V]. This key is
the only statically defensible "missing firmware config message" left, so this lane delivers it as
a **fail-closed candidate** (patch + fire recipe) - **not** as a proven fix: nothing in the static
evidence says key 0x0004 enables the RX data path, and the fire is the discriminator.

Ranking of the three remaining explanations for the RX capture silence (unchanged context, this
lane's result folded in):

1. **A firmware RX-path initialisation that is not reachable from the host message surface of this
   firmware build** - still possible: the init chain sends nothing, the 8 live keys are all
   accounted except 0x0004, so if a host message is the fix it is either 0x0004 or one of the
   unbuilt status-forwarding messages (F4 class). [I]
2. **The RX completion/PPDU descriptor contract between host rings and firmware DMAC** - the
   candidates already refuted on the bench (enable/format/state/transform/WOC class all
   vendor-correct). [V*]
3. **Device/firmware-internal fault** - the stock control proves the device RX path itself works
   with the vendor host, so this is a host-message-compatibility fault class. [V*]

## 2. The message constructors (re-verified)

### 2.1 `hdpp_config_send_event` @0x59c0 [V]

Signature `(descriptor r0, u16 key r1, u16 len r2, data r3)`; body:

```
59c0  push {r4-r9,lr}
59e4  hcc_msg_alloc(len + 16, 0)          ; the +16 = 12-byte HCC header + 4 slack
59f0  msg = [alloc + 0x118]               ; the hcc_msg object carries the header pointer at +0x118
5a00  hdr[6] = 1                          ; *** message id = 1 (group 0 id 1 config event) ***
5a14  hdr[0] = (hdr[0] & 0xf0) | nibble   ; low nibble of hdr[0] = group
5a24  desc[4]                             ; high nibble of hdr[1] = direction/dst from descriptor
5a2c  hdr[1] = bfi(...)
5a34  hdr[2] = desc[6]
5a3c  hdr[3] = desc[1]
5a40  hdr[8] = 0
5a44  strh key  -> hdr[20]                ; *** config key = payload+8 ***
5a48  strh len  -> hdr[22]                ; payload length = payload+10
5a6c  memcpy_s(hdr+24, len, data)         ; payload data at payload+12
5a54  hcc_msg_tx(msg)
```

So every config event is: **group 0, id 1, total = len + 24** (12 header + 8-byte preamble + 2 key
+ 2 len + data; the vendor capture additionally carries a 4-byte `0xff` tail inside the declared
total, see §5.2). The key lives at **header+20 = payload+8**, exactly as the firmware group-0 id-1
handler consumes it (`ctx = lookup(hdr[3]); key = u16 hdr+0x14; data = hdr+0x18`) [V*].

### 2.2 `hmac_config_send_event` @0x5717c + shared builder @0x57090 [V]

Signature `(descriptor r0, u16 key r1, u16 len r2, data r3)`. The shared builder @0x57090 does the
allocation (`len + 16`), writes **`hdr[6] = 1` as a u16** (`strh r8,[r4,#6]`), and returns
`data_ptr = hdr + 12` and the message; `hmac_config_send_event` then writes the key at
`hdr[20]`, the length at `hdr[22]`, and copies the data to `hdr[24]` before `hcc_msg_tx` [V].

### 2.3 The direct builders

77 module functions call a tx primitive (`hcc_msg_tx` 74 sites, `hcc_msg_tx_to_core` 8,
`hmac_hcc_msg_tx_send` wrapper); 57 of them store an immediate id at `hdr+6`. The full list with
ids, plus the `hdr+20` immediates where present, is [TABLES-h2d-builders.md](TABLES-h2d-builders.md)
[V].

## 3. The vendor init chain sends no H2D message

### 3.1 Direct callees of the init entries [V]

| entry | address | direct callees of interest |
| --- | --- | --- |
| `hmac_main_init` | 0x3f6b8 | `hcc_get_state`, `hmac_res_vap_dev_init`, `hmac_res_init`, **3 x `hcc_msg_register_tab_chip`**, `hdpp_main_init`, the hmac module inits (`hmac_acs_init`, `hmac_phy_event_init`, `hmac_spectral_init`, `hmac_csi_init`, `hmac_multiap_init`, `hmac_fsm_init`, `hmac_board_init`, ...), **`hcc_set_state(4)`** |
| `hdpp_main_init` | 0x12e0 | `hdpp_chip_init`, `hdpp_var_init`, `hdpp_hisi_thread_init`, `hcc_queue_register_customer_for_chip/core`, `hcc_msg_register_tab_chip/core` |
| `hdpp_chip_init` | 0x502c | `get_chip_type`, `memset_s`, OAM logs - **no message** |
| `hdpp_var_init` | 0x43f0 | `hdpp_var_alloc`, `hdpp_smp_init`, `hdpp_device/band/vap/user_module_init`, `hdpp_stat_init` - **no message** |

Closure of the four entries to depth 4 = 124 functions; the only HCC calls in that closure are the
registrations above plus one `hdpp_config_send_event` from `hmac_txq_table_addr_sync`
(@0x1af64, key `0x0320`, len 4) reached at depth 4 - and that message is **not** part of
`hmac_main_init`'s boot path (it is called by `hmac_txq_table_init` @0x1b12c). **No
`hcc_msg_alloc`/`hcc_msg_tx` config send is reachable from the init entries' direct call tree** [V].

Consequence: the vendor's boot messages (whatever they are) are issued by asynchronous/runtime
paths after the firmware-ready events, not by the init chain - so "the missing RX-init message" is
not a boot-chain message; if it exists it must be a message from the config-event/ops surface.

### 3.2 Bonus: the D2H registration tables at init [V]

`hmac_main_init` installs three D2H handler tables with `hcc_msg_register_tab_chip`
(`r2` = entry count): `.data+0x584` 28 entries, `.data+0x6d4` 12 entries, `.data+0x764` 8
entries; `wal_main_init` @0x12386c adds a 19-entry table. Entry layout is the 12-byte
`{u32 id; u32 fn; u32 aux}` (fn filled by `R_ARM_ABS32` relocations). First table (ids ->
handlers): 0 `hmac_sdt_up_reg_val`, 1 `hmac_create_ba_event`, 2 `hmac_del_ba_event`,
3 `hmac_event_config_syn`, 5 `hmac_syn_info_event`, 9 `hmac_bandwidth_info_syn_event`,
0xa `hmac_protection_info_syn_event`, 0xb `hmac_ch_status_info_syn_event`, 0xd
`hmac_rx_process_mgmt_event`, ... 0x27 `hmac_pfm_detect_process_event`; second table
(0x16..0x24) includes `hmac_spectral_scan_complete`, `hmac_phy_event_complete`,
`hmac_mgmt_deauth_msg_process`, `hcc_timer_process`, ...; third (9..0x14) includes
`hmac_smps_update_device_capbility`, `hmac_pfm_hiex_rx_local_msg`, `hmac_bsd_update_msg`,
`hmac_d2h_pm_event`, ... [V]. The `r0` argument of the first `hmac_main_init` registration is
a variable (`r7`); the other two are literal 2 and 3, which suggests "chip/core slot" semantics
[I]. This is the D2H **receive** surface only - no sends.

## 4. Config-event senders vs the firmware's live keys

### 4.1 The vendor's g0-id1 key space [V]

266 call sites of the two config-event constructors resolve to **244 distinct immediate keys**;
5 call sites pass a dynamic key (`hmac_config_sync_cmd_common` and four WAL wrappers, all
runtime WMM/EDCA/PM commands). The full key -> builder/function/len table is
[TABLES-config-senders.md](TABLES-config-senders.md). The keys divide into obvious families:
VAP/AP control (`0x64/0x65/0x66/0x67/0x69`, ...), calibration/ALG configs, RSSI/rate/EDCA tuning
(0x100-0x400), monitor/dump commands, and the multi-AP/11v families.

### 4.2 The firmware's live keys and who sends them [V]

Firmware group-0 id-1 handler CA `0x43D58` -> key table A CA `0x10C23C` (217 x
`{u16 key; u16 pad; u32 worker}`); exactly 8 entries have non-NULL workers [V* verified with the
committed `wifi-ctx-create/tools/ctx_create_re.py --tables`, re-run this lane]. Cross-referenced
with the vendor senders [V]:

| live key | table A row | firmware worker | vendor sender found by this lane | our driver sends it? |
| ---: | ---: | ---: | --- | --- |
| 0x0004 | A[0] | CA 0x811CD | **none** (see 4.3) | **no** |
| 0x0064 | A[1] | CA 0x449E4 | `hmac_config_add_vap_sync_all` @0x15becc (len dynamic) | yes - `h2d_ctx_create` (g0 id1 key 0x64, 48 B frame) and the VAP-add family [V*] |
| 0x0065 | A[2] | CA 0x46394 | `hmac_config_start_vap_event` @0x15afdc (len 12) | yes - VAP start [V*] |
| 0x0066 | A[3] | CA 0x4455A | `hmac_config_del_vap` @0x15a924 | no (no VAP delete in the bench ladder) |
| 0x0067 | A[4] | CA 0x45F74 | `hmac_config_down_vap` @0x15d79c | no |
| 0x0069 | A[5] | CA 0x839B4 | `hmac_set_mode_event` @0x15b080 (len 4) | no |
| 0x00D8 | A[41] | CA 0x81038 | `hmac_config_mib_amsdu_aggregate_ative` @0x6269c (len 20) | yes - `h2d_txq_sync` (the captured first post-ready vendor frame) [V*] |
| 0x0320 | A[164] | CA 0x81444 | `hmac_txq_table_addr_sync` hdpp builder @0x1af64 (len 4) | yes - `h2d_txq_addr_sync` [V*] |

**Important correction to the inherited naming:** the captured live vendor first post-ready frame
("cmd 0x00d8, len 0x14") is the AMSDU-AMPDU-aggregation MIB config (key 0xD8), not the TXQ
address sync (which is key 0x320, len 4). Our driver's `h2d_txq_sync` replicates that frame
byte-exactly, so the reproduction stands; only its attribution in the earlier lane's text was
wrong [V]. The context-create lane's decision to send key 0x64 before key 0xD8 is still correct
(the 0xD8 worker dereferences `ctx+0x190`, which only the 0x64 create helper allocates) [V*].

### 4.3 The one unaccounted live key: 0x0004 [V]

Exhaustive negative evidence for a sender:

1. No `hmac_config_send_event` or `hdpp_config_send_event` call site passes key 4 (all 266 sites
   scanned; the 5 dynamic sites are runtime WMM/PM wrappers whose callers pass no key 4 either) [V].
2. No function anywhere builds a g0-id1 frame with an immediate `hdr[6]=1` **and** an immediate 4
   at `hdr+20/hdr+22` (header-constant scan over all 4,245 disassembled functions) [V].
3. The only `hdr[6]=1` immediate builders are the two config-event constructors, and both take
   the key from their caller (already covered by 1) [V].
4. The firmware's own boot task does not create the "host context": the create helper is invoked
   at firmware CA `0x48862` with fixed id `0x12` and a zeroed data block (type 0 -> no
   `+0x190` allocation), so key 4 cannot be an internal firmware post either [V*].

Therefore key 0x0004 has no sender in the shipped vendor kernel modules. Two readings remain:
(a) a code path not present in the shipped modules (not possible for the HCC data path - all HCC
senders are in `wifi.ko`; the plat module imports no HCC symbol), or (b) the key is dead in this
vendor build. A stock-boot H2D trace would settle it; it is not part of this host-only lane.

## 5. The candidate message (the deliverable)

### 5.1 Firmware worker CA 0x811CD (file 0x411CD, Thumb) - full body [V]

```
000811cc  cbz   r2, #0x811dc            ; data pointer NULL -> refuse
000811ce  ldr.w r3, [r0, #0x190]        ; r3 = ctx->buffer (created by the 0x0064 helper)
000811d2  ldr   r2, [r2]                ; first word of the config data (host-written)
000811d4  movs  r0, #0
000811d6  strb.w r2, [r3, #0x52]        ; ctx_buffer[0x52] = data[0]
000811da  bx    lr                      ; success
000811dc  movw  r0, #0x8b2d             ; -29909 = project-wide "invalid parameter"
000811e0  bx    lr
```

Properties: requires hdr[3]-selected module context with a non-NULL `+0x190` buffer (i.e. our
`h2d_ctx_create` with `data[4]=4` must have been consumed first); writes exactly one byte; reads
only `data[0]`; never dereferences a host-supplied pointer; returns 0 on success [V]. A reader
of that byte was not found by a linear scan (961 `[reg,#0x190]` loads, none followed by a
`ldrb [reg,#0x52]` within 120 B in the main code region), so the field's consumer is [U] - it may
be read through a register passed as an argument.

### 5.2 Wire format for the candidate [V geometry from phase20/38 capture + §2]

```
offset  size  value
0       1     0x00            ; group 0
1       1     0x00            ; direction nibble (our carrier: dst 0)
2       1     0x00
3       1     0x00
4       2     total           ; 12 header + 8 preamble + 2 key + 2 len + 4 data + 4 tail = 32
6       2     0x0001          ; message id 1 = config event
8       1     0x00
9       1     0x00
10      2     0x5a5a          ; transport tag (vendor SR constant; our frames library writes it)
12      8     00 00 00 00 01 00 00 00   ; inherited preamble (identical to ctx_create/txq frames)
20      2     0x0004          ; *** the config key ***
22      2     0x0004          ; data length (u32 value)
24      4     01 00 00 00     ; data[0] = 1 (the byte the worker writes at ctx+0x190+0x52)
28      4     ff ff ff ff     ; inherited tail (vendor capture geometry)
```

Vendor-capture cross-check: the phase20/phase38 captured key-0xD8 frame is
`00 01 00 04 30 00 01 00 00 00 5a 5a | 00 00 00 00 01 00 00 00 | d8 00 14 00 | data 20 B | ff ff ff ff`
= total 0x30, i.e. `28 + data_len`; the candidate uses the same geometry with `data_len = 4` ->
total 0x20 [V]. The firmware's handler bounds (`hdr[5]>>1&7 <= 3`, total <= `0x62` payload) are
satisfied [V*].

### 5.3 Risk analysis (fail-closed design)

* **Precondition:** the message is only emitted after the 0x64 context-create announce was
  consumed and the TXQ config sync is at least sent (the context buffer must exist, else the
  worker returns `0x8b2d` and only logs; no crash path).
* **One message per boot**, never retried after a refused/failed post (same policy as the H2D
  module's one-frame rule); module params default OFF.
* **No pointer payload:** the firmware handler reads one word; the only bytes we control are the
  key/len/data values above.
* **Read-back:** the announce-consumption watch (out[0] clears) is the observable; on timeout the
  lane closes and nothing is retried.

### 5.4 What the candidate is not

* It is not the vendor's `smac_msg_proc_enable_trx_req` / `rx_ring_reset_req`: those names are a
  firmware-internal SMAC debug string pool, and the corresponding host messages do not exist in the
  shipped module (already concluded by the rx-format lane; re-confirmed here on the sender side) [V].
* It is not the F4 status-forwarding class (g0 id0 / g0 id7): that is a separate, already
  documented host->firmware gap (rx-format REPORT §11) and is not implemented by this patch.
* It does not change any MAC register, ring or buffer (those aspects were proven vendor-correct by
  the rx-vendor-diff lane) [V*].

beyond these; the only live-key gap is 0x0004 (§4.3).

## 7. Honest verdict and next steps

* The "missing firmware RX-init message" is **not** in the vendor init chain - the chain has no
  H2D sends. The hypothesis survives only as "a runtime config the vendor sends and we don't";
  in the live-key space exactly one such message is unaccounted: key 0x0004.
* The delivered patch is a **cheap safe discriminator**. If the fire shows `frames>0` + page
  golden with only this message added, the firmware RX path needs this context byte; if not, the
  candidate is refuted and the next steps are (1) the F4 status-forwarding class (g0 id0 stub is
  safe), (2) a stock-boot H2D trace (bench, attended) to settle whether the vendor sends key
  0x0004 at all, (3) the DMAC/firmware completion-descriptor contract (deeper firmware decode).
* What remains for the lane: the module build in the fired association tree + the attended fire
  (Lead). The patch is host-tested and applies cleanly to the committed `wifi-h2d-send/src` tree;
  a 3-hunk port to the association tree is documented in FIRE-RECIPE.md.
