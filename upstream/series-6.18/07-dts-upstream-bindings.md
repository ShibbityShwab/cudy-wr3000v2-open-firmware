# 07 - Upstream DTS bindings cleanup and hardware-regression record

This note records (a) the 2026-11-21 **hardware regression** caused by the
first active-DTS cleanup, (b) the conservative comment-only cleanup that
replaced it (active content byte-identical to the hardware-verified board), and
(c) the optional deltas that may be pursued later, each of which needs its own
hardware-tested patch.  The previous aggressive cleanup record is superseded.

- single source: `target-skeleton/dts/luofu-r116.dts` (hardware-verified
  active content; comments only were removed);
- upstream artefact: `dts-series/0001-arm-dts-hisilicon-luofu-r116-loader-handoff.patch`
  (DTS-0001), regenerated byte-identically from the single source;
- the image build still runs `Build/luofu-pad-dtb` (the DTB totalsize is
  unaligned; see section 5);
- no active DTS change may be accepted from host checks alone: **the image must
  be boot-tested on the unit after every active-DTS change.**

## 1. Hardware regression: the active-DTS cleanup did not boot

The first cleaned DTS (submodule commit `538377c`) changed active
devicetree content, not just prose.  The resulting image **`6f19c6d6`**
(DTB 11,702 B padded to 11,704 B) was installed on the unit (pair b) with the
verified stock-telnet installer and captured on UART:

- evidence: `build/evidence-bench-gates/2026-11-21-cleaned-dts-regression.log`,
  sha256 `15dc318865ddc908e32ba8fa6d09d6a3c0f357d86a1d801b623af3bf17f21918`;
- the 6.18 kernel booted with SMP (2 CPUs), the loader hand-off was consumed and
  the early markers were consumed;
- MTD partition registration started at ~0.90 s, but the 17 partition prints
  stretched to ~24.55 s with growing delays (rootfsa -> rootfsb 5.58 s,
  rootfsb -> rootfs_data 5.58 s, rootfs_data -> upgrade 5.28 s);
- `luofu-reboot` and `luofu-wdt` never probed; at ~24.55 s the unit
  reset (compatible with the U-Boot ~30 s watchdog) and fell back to stock
  pair A.

Known-good reference on the same unit, same kernel config and userspace, image
**`7421bb7a`** (pre-clean DTS; DTB 13,041 B padded 13,048 B): partition
scan 0.93-1.16 s, `luofu-reboot` registered 2.28 s, `luofu-wdt` 2.30 s,
ubi attach 2.68 s, init 3.01 s.

**Conclusion:** prose-only changes are safe; the active-DTS edits (renames,
removals, model/compatible/alias changes) were not hardware-tested and caused
the regression.  Host-side checks (patch application, dtc compile, contract
values, DTS-0001 identity, pad-dtb) are necessary but **not sufficient**.  The
active DTS was therefore reverted to the known-good content; the earlier
aggressive cleanup is not hardware-validated and must not be used as-is.  The
conservative cleanup is commit `7ae18f2` (section 2); afterwards the
boot-tested TWD level-high delta was adopted in commit `5b401c1` (section
6.1), which is the current devicetree final.

## 4. Binding review of the known-good DTS (kept deliberately)

The conservative DTS keeps several known binding deviations because they were
present in the hardware-verified DTB and are not prose:

1. `flashinfo@80600000` uses the vendor compatible
   `"hsan,flashinfo_reserved"`; it is the stock loader contract and has no
   upstream binding.
2. The bdinfo MAC source uses `fixed-layout`/`mac-base` nvmem cells,
   which are v6.19 bindings on a 6.18 baseline.
3. The switch node's unit address (`@11000000`) does not match its first
   `reg` entry, because the in-series binding puts the two DDR regions
   first; the node name is kept until the binding is reworked and hardware-tested.
4. `gpio-keys-polled` child names (`reset`/`wps`) and the
   gpio-leds child names (`led-status`...) do not use the preferred
   standard names; kept until the rename is boot-tested (optional deltas 2/3).
5. The TWD timer interrupt was changed to the standard
   `GIC_PPI 13 (GIC_CPU_MASK_SIMPLE(2) | IRQ_TYPE_LEVEL_HIGH)` encoding after
   the measured read-only PPI data and a boot-test PASS (image f6685b80;
   section 6.1).  The measured GICD_ICFGR1 `0b11` value remains documented as
   the hardware fact.
6. The root compatible does not carry `cudy,wr3000-v2` yet (delta 1).
7. The draft in-series bindings/drivers are not upstream, so the board DTS
   cannot be submitted before they are accepted.

There is **no dtschema/dt-validate/yamllint tooling** available in this
checkout (no module, binary, pip or yamllint), so a real `make dtbs_check` /
`dt_binding_check` run could not be made.  The check performed is:
cpp+dtc compile (RC=0, 0 diagnostics), the extra dtc warning sets
`unit_address_vs_reg simple_bus_reg avoid_unnecessary_addr_size
unique_unit_address_if_enabled` (0 warnings), a byte-identity comparison of
the compiled DTB against the known-good DTB, and a manual required-property/name
review against the in-series YAMLs and the standard 6.18 bindings.

### 6.1 TWD timer interrupt flags - CLOSED (boot-tested, image f6685b80)

Measured on hardware on the previous baseline 7421bb7a (GICD base
`0x10181000`):

| register | value |
| --- | --- |
| GICD_CTLR | `0x00000001` |
| GICD_TYPER | `0x0000fc25` |
| GICD_ICFGR0 | `0xaaaaaaaa` |
| GICD_ICFGR1 | `0x7dc00000` |
| GICD_ICFGR2 | `0x55555555` |

On 7421bb7a the kernel reported `GIC-0 29 Edge twd`; ID 29 is TWD PPI 13
(16 + 13).  The GICD_ICFGR1 field for ID 29 (bits 27:26) reads `0b11`, a
nonstandard/reserved encoding, but **GIC-400 PPI configuration is read-only/
fixed by the SoC integration**, so the devicetree flag does not reprogram
hardware.  Standard Cortex-A9 platforms (e.g. vexpress-v2p-ca9) use
`IRQ_TYPE_LEVEL_HIGH` for the TWD timer (0xf04 flags for 4 CPUs; the
equivalent here is `GIC_CPU_MASK_SIMPLE(2) | IRQ_TYPE_LEVEL_HIGH` = `0x304`).

The level-high draft was applied and boot-tested: image **f6685b80**, installed
with the verified telnet installer (PASS; pair b, selector 0x11), boots
6.18.60 with 2 CPUs, `/proc/interrupts` now reports
`GIC-0 29 Level twd` (was `Edge`), TWD counts increment ~100 Hz on both
CPUs, host ping 20/20 0% loss, no Oops/BUG/Kernel panic/RCU stall, uptime
stable.  Adopted in commit `5b401c1`; current final DTS 700 lines sha256
`13427d8e...`; DTB 13,041 B sha256 `4fde76df...` (pad 13,048 B
sha256 `4b50de73...`); DTS-0001 sha256 `e9c9ed58...` (713 lines).
Image f6685b80 supersedes 7421bb7a for DTS purposes; 7421bb7a remains the
previous verified baseline.

**Not claimed / out of scope (not counted among the five blockers):** pinctrl
consumer states, consumer clocks, the A/B boot-selector protocol beyond the
measured `0x10`/`0x11` cell, LED function/color descriptions, Wi-Fi and
thermal support, and the unused vendor blocks (wired-first target).

**Current devicetree final:** commit `5b401c1` (conservative cleanup

## 7. Single-source and regeneration

Only `target-skeleton/dts/luofu-r116.dts` is the source.  After any change,
regenerate DTS-0001 and the recorded hashes:

    python3 tools/gen-dts-series-patch.py \
        --pristine <extracted linux-6.18.60> \
        --target-dts ../../target-skeleton/dts/luofu-r116.dts \
        --out dts-series/0001-arm-dts-hisilicon-luofu-r116-loader-handoff.patch

then run `tools/check-release-line.sh --use-tree <pristine> <workdir>`,
refresh `validation/sha256sums.txt`, and **boot-test the rebuilt image**
before treating any active-DTS state as hardware-validated.
