### 0001/17  ARM: mach-hisilicon: add Hi5671Y "luofu" machine support

Status: RFC

~~~
ARM: mach-hisilicon: add Hi5671Y "luofu" machine support

Add a machine descriptor for the HiSilicon Hi5671Y "luofu" SoC and the
Cudy WR3000 v2.0 (board R116).  The platform is described entirely by
devicetree; the descriptor only matches the board and replays the PL310
AUX value that the vendor bootloader programs (0x430001 with mask
0xffb0fffe, which is also what enables the cache controller through
l2x0_of_init()), so the machine code itself programs no hardware.

ARCH_LUOFU is defined in a new arch/arm/mach-hisilicon/Kconfig under the
existing upstream ARCH_HISI symbol rather than in mach-hisi, because
this SoC is not part of the hi3xxx/hiP0x family that directory
implements; the new machine directory keeps the platform code separate
and the board stays a pure devicetree platform.

The machine is UP-only for now.  The vendor devicetree's enable-method
is the vendor-private "hisilicon,hsan_smp" and there is no mainline
smp_ops for the second Cortex-A9, so .smp is left unset and a UP boot is
the documented first posture.  .restart is likewise unset until the CRG
reset sequence has been validated (the later restart-driver patch
provides it as a separate, provisional driver).

This is an RFC platform series: the machine has been host-compiled only
and has never booted.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>
~~~

### 0002/17  ARM: luofu: add ARCH_LUOFU to Kconfig and set its text offset

Status: RFC

~~~
ARM: luofu: add ARCH_LUOFU to Kconfig and set its text offset

Wire the new arch/arm/mach-hisilicon directory into the ARM build: source
its Kconfig, add the machine directory and set
textofs-$(CONFIG_ARCH_LUOFU) := 0x00608000.

The text offset is a hardware contract, not a preference.  The stock
loader stages the kernel slot at 0x83200000 and the decompressor computes
(pc & 0xf8000000) + TEXT_OFFSET, so 0x00608000 makes the kernel link and
start at 0x80608000, which is the uImage load/entry address the loader
uses.  That contract is derived and asserted by the image recipe rather
than hardcoded.

0x00608000 is not encodable as an ARM immediate, so this patch only
builds together with the following early-boot change.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

### 0003/17  ARM: head: materialize TEXT_OFFSET with mov_l

Status: RFC

~~~
ARM: head: materialize TEXT_OFFSET with mov_l

TEXT_OFFSET is platform specific and the 0x00608000 offset required by
the luofu platform cannot be encoded as an ARM immediate.  The early boot
code uses #TEXT_OFFSET arithmetic in four places, which makes such a
platform unbuildable.

Replace the immediate arithmetic with the kernel's own mov_l macro, which
emits movw/movt on ARMv7 and a literal load on older CPUs.  The linker
textofs contract and the resulting load address are unchanged for every
existing platform.  For the luofu platform the built kernel's
disassembly was checked at all four sites and materializes 0x00608000,
with _text = stext = 0xc0608000 and the load/entry address 0x80608000.

This is an ARM core patch carried by a single-platform series; review by
the ARM maintainers is expected before the platform can rely on it.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

## Group 2 - peripheral drivers, ready for review

### 0004/17  clk: hisilicon: add Luofu CRG clock and reset controller

Status: ready-for-review

~~~
clk: hisilicon: add Luofu CRG clock and reset controller

Add a driver for the CRG (Clock Reset Generator) of the HiSilicon
Hi5671Y "luofu" SoC.  The CRG is a 4 KiB system-controller page whose
clock-gate bits (0x14/0x20), reset bits (0x2c/0x30/0x34) and watchdog
words (0x50/0x64/0x70/0x100) are interleaved, so the node is modelled as
"hisilicon,luofu-crg", "syscon", "simple-mfd" and this driver uses the
parent syscon regmap: it never claims or maps the MMIO page, and neither
does the watchdog child.  That is also what removes the lab lane's
second-claim -EBUSY workaround.

The 16 gate clocks are described by driver data indexed by the clock IDs
in include/dt-bindings/clock/hisilicon,luofu-crg.h; the devicetree only
carries the index, not the gate geometry.  Resets keep the two-cell
(register offset, bit) specifier documented in the binding, and the
offsets are range-checked to the three reset words so that a devicetree
can never write the watchdog, reboot, soft-reset, mux or PLL words by
accident.

Deliberately not implemented: the per-gate parent/PLL/mux model (rates
are not modelled yet; every gate is currently parented on the APB clock),
named reset IDs, and the reboot/soft-reset/mux/PLL words.  The gate
geometry is provisional until it is confirmed against the running vendor
kernel, and the binding says so.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check; never run on hardware.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

### 0005/17  watchdog: luofu: add Hi5671Y watchdog support

Status: ready-for-review

~~~
watchdog: luofu: add Hi5671Y watchdog support

Add a watchdog driver for the watchdog function of the luofu CRG page.
The watchdog has no reg of its own: it is a child of the CRG syscon node
and uses the parent regmap, so the CRG page is mapped exactly once and
the lab lane's devm_ioremap() workaround is gone.

The register values are the vendor's own hwver-2 data, matched against
the live register state, and are kept in the driver rather than exposed
as vendor-only devicetree properties: enable writes to 0x64, timeout is
the (secs - 1) field at bits [18:10] of 0x50, and 0x70 keeps the timer
fed.  The encoding is validated against the vendor kernel's live
0x30007400 / 30 s pair.

No restart handler and no interrupt: the reset path is unverified and a
restart handler in a watchdog driver could arm the timer, and the
status/IRQ semantics of 0x100 are not decoded.  Probe performs no
register access; the hardware is written only from the standard watchdog
operations after userspace opens the device.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check; never run on hardware.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

### 0012/17  thermal: add Luofu thermal sensor driver

Status: ready-for-review

~~~
thermal: add Luofu thermal sensor driver

Add a read-only thermal sensor driver for the HiSilicon Hi5671Y "luofu"
SoC.  The die temperature is the low 16 bits of the word at offset
0x24, converted with the vendor v4 formula

    ((165 * raw - 32835) / 100) * 1000 - 40000   millidegrees

reproduced operation for operation, including the truncating division,
so the reported values match the vendor kernel.  The sensor is
registered as an of-thermal sensor with
devm_thermal_of_zone_register().

The thermal zone, its trips (115 C passive, 125 C critical, 3 C
hysteresis) and the 1 s polling delay are board devicetree data.  The
threshold, interrupt, enable and trim registers are not decoded and are
not written; the node claims no interrupt and the driver has no write
path at all.

### 0014/17  clk: hisilicon: fix Luofu CRG reset polarity

Status: ready-for-review

~~~
clk: hisilicon: fix Luofu CRG reset polarity

The reset class of the luofu CRG page is active-low: a reset line is
released by SETTING its bit and driven into reset by CLEARING it.  The
initial CRG driver implemented the opposite, so reset_control_deassert()
from any consumer would have asserted the line instead of releasing it.

The polarity is measured, not assumed: the live census of 0x14880034
reads 0x000ff309 with both PCIe root complexes up, i.e. the four RC0
reset bits are set in the released state.  Swap the two operations in
luofu_crg_reset_set() and invert reset_control_status() accordingly.

This fixes the FMC, MDIO/GEMAC and PCIe consumers.  They all use the
standard reset API and need no change.

Host-compiled against linux-6.18.60; the polarity itself was measured on
the vendor kernel, but this driver has never run on hardware.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

### 0006/17  spi: spi-luofu-fmc: add Luofu FMC SPI-NAND controller

Status: RFC

~~~
spi: spi-luofu-fmc: add Luofu FMC SPI-NAND controller

Add the flash-memory controller of the HiSilicon Hi5671Y "luofu" SoC as
a SPI-MEM controller.  On this board the FMC drives an ESMT F50L1G41LC
SPI-NAND die; the mainline SPI-NAND stack (drivers/mtd/nand/spi) owns
chip detection, on-die ECC, the OOB layout, bad-block handling and
partition parsing, so this driver only implements the command engine,
the DMA engine for page/OOB transfers and the memory-mapped data window.
The root filesystem of the board lives on this controller.

The vendor devicetree properties become standard SPI properties
(spi_cs becomes the child's reg, enable-quad-mode becomes
spi-tx/rx-bus-width); bus_id is dropped.  The vendor driver's custom
mtd_info, sysctrl breadcrumbs, JFFS2/UBI in-tree hacks and "read ECC
off" flag are not carried over.

Deliberately not done, because none of it has been run on hardware: the
fifteen further vendor init words whose meaning is unknown are not
written, the die is not reset and its quad-enable bit is untouched, and
there is no interrupt.  The FMC ECC semantics (host ECC vs on-die
pass-through), the OOB bytes the DMA engine returns and whether the
SPI-NAND core's reset clears the quad-enable bit remain unverified.

This is an RFC: the storage path is critical and the semantics above
must be confirmed before merge.  The controller also depends on the
ESMT F50L1G41LC chip entry, which is a v6.19 addition and is not in
linux-6.18.60, so it must be submitted after that entry (or with it) and
is only buildable today through the OpenWrt generic backport.

Host-compiled against linux-6.18.60, binding checked with

### 0011/17  pinctrl: hisilicon: add Luofu peripheral pin controller

Status: RFC

~~~
pinctrl: hisilicon: add Luofu peripheral pin controller

Add a pin controller for the peripheral IOMUX of the HiSilicon Hi5671Y
"luofu" SoC: 37 pins, 24 groups and 24 functions in two register windows
(mux 0x14900100/0x3c, cfg 0x14940000/0x100), with pinmux, pinconf and
generic devicetree state parsing.

The tables were re-verified from the vendor pin controller module for
this SoC: the per-pin five-hit mux table, the group-level mux fields,
cfg offset = 4 * pin and the six generic pinconf fields (bias pull-up/
pull-down, raw 3-bit drive strength, schmitt, input enable, output

selecting a function walks the vendor algorithm: clear every hit first,

UART nodes need is not measured; guessed states could remux the console
or NAND.  The drive-strength mA mapping is also unknown, so the raw
field value is used.

This is an RFC: the probe-time/default pin state and consumer-state
requirements are open and no state has ever been applied on hardware.

### 0013/17  PCI: dwc: add Luofu PCIe host controller

Status: RFC

~~~
PCI: dwc: add Luofu PCIe host controller

Add the DWC-based PCIe host controller for the two root complexes of the
HiSilicon Hi5671Y "luofu" SoC (RC0 at 0x10160000, RC1 at 0x10164000).
Each root complex is a DesignWare core with a SoC wrapper for the
root-complex mode and LTSSM enable, plus a dedicated 4 KiB configuration
window that has to be reached through the outbound iATU (CFG0) rather
than ECAM, so the DWC host framework's ECAM path does not apply.

The driver programs the iATU viewports from the devicetree ranges, does
only 4-byte-aligned 32-bit DBI/configuration accesses, and encodes the
measured hard rules: the misc window is write-only and must never be
read (a userspace read of 0x10161000 panicked the board), and sub-word
or misaligned accesses fault.  The gate clock and the four active-low
resets per root complex come from the CRG.

This is an RFC: the wrapper store semantics, the iATU-enable/LTSSM bit
interaction, the DWC version word, endpoint power, MSI/INTx and real
enumeration have never been validated.  The Wi-Fi endpoint behind RC0
has no mainline driver and is out of scope; the devicetree nodes stay
disabled.  Never run on hardware.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check.

### 0017/17  soc: hisilicon: add Luofu A/B boot selector

Status: RFC

~~~
soc: hisilicon: add Luofu A/B boot selector

Add a sysfs interface to the A/B boot-selector cell in the SYSCTRL page
of the HiSilicon Hi5671Y "luofu" SoC (0x10100000 + 0x0c08 on this
board).  The stock loader boots the firmware pair named by the low byte
and keeps the recorded value sticky across resets: 0x10 is the A pair,
0x11 the B pair, 0x21 a manual/recovery handover written by the stock
sysenv interface, and 0x00 the power-on value.

current_pair decodes the cell; next_pair accepts only the two measured
recorded-pair values and verifies the read-back.  Probe performs no
register access, and the SYSCTRL page stays a shared syscon with the
machine-restart driver.

This interface is needed by the A/B sysupgrade path, which is host-only
so far.  It is an RFC: the post-boot selector protocol, the env-block
re-stamp and the first boot of a written pair are not measured, and the
sysfs ABI has to be reviewed and frozen before it can be relied on.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check and checkpatch; never run on hardware.

### 0010/17  power: reset: add Luofu machine restart driver

Status: RFC (provisional reset)

~~~
power: reset: add Luofu machine restart driver

Add a restart driver for the HiSilicon Hi5671Y "luofu" SoC.  The SoC has
no ARM architectural reset that takes the whole chip down; the vendor
sequence saves the SYSCTRL A/B boot-selector cell, asks the CRG for a
software reset and falls back to the CRG watchdog if the command does
not take.  Both pages are syscon nodes shared with the CRG/watchdog and
boot-selector drivers, so this driver never maps or claims MMIO itself.

Measured facts: the selector cell at SYSCTRL+0xc08 uses 0x10 for the A
pair and 0x11 for the B pair and is sticky across resets, so the driver
writes back only the value it has just read (a write-same) and leaves
unrecognised values alone; it therefore cannot move the board to another
slot.  The CRG reboot command pair is the vendor devicetree's own value
and is PROVISIONAL: the write order and register width have never been
measured.  It is confined to the reboot word and bounded by a 1 s
watchdog fallback instead of parking forever, which is exactly the
failure mode that stranded the board on the bench.

This is an RFC: the reset sequence must be validated on hardware with
recovery armed before it can be merged.  Probe performs no register
access; never run on hardware.

Host-compiled against linux-6.18.60, both bindings checked with
dt_binding_check.

### 0016/17  net: ethernet: hisilicon: add Luofu switch probe skeleton

Status: draft (do not merge)

~~~
net: ethernet: hisilicon: add Luofu switch probe skeleton

Add the D1a resource/binding skeleton for the internal LSW switch of the
HiSilicon Hi5671Y "luofu" SoC.  The vendor tree describes the switch as
two nodes, but it is one device: the binding is one node with the 15
recovered MMIO windows (five queue-manager and ten classifier/
forwarding, 512 KiB each), two CRG gate clocks, four CRG reset lines and
an ethernet-ports port model.  The vendor queue/flow DDR regions are not
modelled because their live base is unknown.

as DSA: there is no CPU-port tag in the recovered model and every wired
port already has its own netdev.  The recovered register, queue and
port-id model has never been measured on this board, and an access to an
unknown part of the block can cut the CPU/console path.

probe() validates the resources and the port model, then refuses with
-EOPNOTSUPP.  No register is read or written, no clock/reset is driven,
no netdev or switchdev notifier is registered, and the node stays
disabled.  This is an RFC and not mergeable; the attended inventory and
a reviewed write set (LSW-SPEC.md D1b-D1d) are required first.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check.
