reset sequence has been validated (the later restart-driver patch

### 0002/26  ARM: luofu: add ARCH_LUOFU to Kconfig and set its text offset

Status: RFC

~~~
ARM: luofu: add ARCH_LUOFU to Kconfig and set its text offset

Wire the new arch/arm/mach-hisilicon directory into the ARM build: source
its Kconfig, add the machine directory and set
textofs-$(CONFIG_ARCH_LUOFU) := 0x00608000.

The text offset is a hardware contract, not a preference.  The stock
loader stages the kernel slot at 0x83200000 and the decompressor computes
(pc & 0xf8000000) + TEXT_OFFSET, so 0x00608000 makes the kernel link and
start at 0x80608000, which is the uImage load/entry address the loader
uses.  That contract is derived and asserted by the image recipe rather
than hardcoded.

0x00608000 is not encodable as an ARM immediate, so this patch only
builds together with the following early-boot change.

### 0003/26  ARM: head: materialize TEXT_OFFSET with mov_l

Status: RFC

~~~
ARM: head: materialize TEXT_OFFSET with mov_l

TEXT_OFFSET is platform specific and the 0x00608000 offset required by
the luofu platform cannot be encoded as an ARM immediate.  The early boot
code uses #TEXT_OFFSET arithmetic in four places, which makes such a
platform unbuildable.

Replace the immediate arithmetic with the kernel's own mov_l macro, which
emits movw/movt on ARMv7 and a literal load on older CPUs.  The linker
textofs contract and the resulting load address are unchanged for every
existing platform.  For the luofu platform the built kernel's
disassembly was checked at all four sites and materializes 0x00608000,
with _text = stext = 0xc0608000 and the load/entry address 0x80608000.

This is an ARM core patch carried by a single-platform series; review by
the ARM maintainers is expected before the platform can rely on it.

### 0004/26  clk: hisilicon: add Luofu CRG clock and reset controller

Status: ready-for-review

~~~
clk: hisilicon: add Luofu CRG clock and reset controller

Add a driver for the CRG (Clock Reset Generator) of the HiSilicon
Hi5671Y "luofu" SoC.  The CRG is a 4 KiB system-controller page whose
clock-gate bits (0x14/0x20), reset bits (0x2c/0x30/0x34) and watchdog
words (0x50/0x64/0x70/0x100) are interleaved, so the node is modelled as
"hisilicon,luofu-crg", "syscon", "simple-mfd" and this driver uses the
parent syscon regmap: it never claims or maps the MMIO page, and neither
does the watchdog child.  That is also what removes the lab lane's
second-claim -EBUSY workaround.

The 16 gate clocks are described by driver data indexed by the clock IDs
in include/dt-bindings/clock/hisilicon,luofu-crg.h; the devicetree only
carries the index, not the gate geometry.  Resets keep the two-cell
(register offset, bit) specifier documented in the binding, and the
offsets are range-checked to the three reset words so that a devicetree
can never write the watchdog, reboot, soft-reset, mux or PLL words by
accident.

Deliberately not implemented: the per-gate parent/PLL/mux model (rates
are not modelled yet; every gate is currently parented on the APB clock),
named reset IDs, and the reboot/soft-reset/mux/PLL words.  The gate
geometry is provisional until it is confirmed against the running vendor
kernel, and the binding says so.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check; never run on hardware.

### 0014/26  clk: hisilicon: fix Luofu CRG reset polarity

Status: ready-for-review

~~~
clk: hisilicon: fix Luofu CRG reset polarity

The reset class of the luofu CRG page is active-low: a reset line is
released by SETTING its bit and driven into reset by CLEARING it.  The
initial CRG driver implemented the opposite, so reset_control_deassert()
from any consumer would have asserted the line instead of releasing it.

The polarity is measured, not assumed: the live census of 0x14880034
reads 0x000ff309 with both PCIe root complexes up, i.e. the four RC0
reset bits are set in the released state.  Swap the two operations in
luofu_crg_reset_set() and invert reset_control_status() accordingly.

This fixes the FMC, MDIO/GEMAC and PCIe consumers.  They all use the
standard reset API and need no change.

Host-compiled against linux-6.18.60; the polarity itself was measured on
the vendor kernel, but this driver has never run on hardware.

### 0019/26  clk: hisilicon: add the Luofu CRG clock tree

Status: ready-for-review (read-only clock tree)

~~~
clk: hisilicon: add the Luofu CRG clock tree

Extend the CRG clock provider of the HiSilicon Hi5671Y "luofu" SoC with
the clock tree that the initial CRG clock/reset controller deliberately
left out: the 16 gate clocks now hang off their real input clocks, and
the two PLLs and the two muxes of the CRG page are registered as
read-only clock outputs of the same provider.

The gate parents are decoded from the vendor devicetree
(MISC-SOC-BLOCKS.md section 5.2): sfc, gpio0/gpio1, i2c0, led_pwm and
pcie0/pcie1 on apb_clk; gemac_clk0..4 and mdio_clk0 on gemacN_clk;
lsw_dp_clk0 on lsw_dp_clk; lsw_pfe_clk0 on lsw_pfe_clk; pie_clk0 on
ahb_clk.  The provider does not guess those names: it resolves the
seven input clocks from the node's clocks/clock-names with
of_property_match_string() and of_clk_get_parent_name(), and the
binding now requires both properties.  The gate register/bit geometry
remains driver data.

The two PLLs (control words at 0x198 and 0x1e0, shared status word at
0x90 bits 30/27) and the two muxes (0x138 bits 3 and 1) are registered
as read-only clocks with the appended indices LUOFU_CLK_PLL_CPU (16),
LUOFU_CLK_PLL_LSW (17), LUOFU_CLK_CPU_MUX (18) and
LUOFU_CLK_EFUSE_MUX (19); LUOFU_CLK_NR becomes 20.  Appending the IDs
does not renumber the existing gate ABI.

The PLL rate equation is decoded from the vendor hi_clk.ko
(hi_pll_recalc_rate: parent * (int + frac / 2^24) / fbdiv, then the two
divider-select fields with the absent vendor "div-factor" term as 0)
and cross-checked against the vendor DT field layout.  The provider
implements recalc_rate and is_enabled only: there is no set_rate, and
no PLL or mux enable/disable.  The on-board control words have never
been read back on this board, so the decoded rates remain read-only
and unmeasured.  The vendor writer's busy-bit/re-lock protocol is
decoded but not implemented because the feedback-word encoding is not
verified, and a wrong PLL store can hang the CPU.

The muxes are read-only for the same safety reason.  0x138 bit 3
selects the CPU clock source between the two PLLs and must never be
writable; bit 1 is the efuse ring source, which only the vendor efuse
programming path ever switches and which this tree does not port (the
efuse cells are one-way fences and key material).  set_parent() returns
-EOPNOTSUPP for both, and the parent tables are decoded from the vendor
devicetree, never measured.

Gates are registered with CLK_IGNORE_UNUSED so that
clk_disable_unused() cannot gate a clock the bootloader left enabled
(the NAND boot path is behind the SFC gate).  Probe stays free of
register writes; the clock words are only read when a consumer asks
for a rate, a parent or a status.

This patch adds no Kconfig symbol and no config line: it only extends
the existing CONFIG_LUOFU_CRG driver and its binding and clock-ID
header.

Host-compiled against linux-6.18.60 in the target lane (0 warnings,
0 errors); the extended binding passes dt_binding_check.  The driver
has never run on hardware: no PLL rate, PLL status, mux parent or gate
state is measured, and there is no Tested-by.

### 0017/26  soc: hisilicon: add Luofu A/B boot selector

Status: RFC

~~~
soc: hisilicon: add Luofu A/B boot selector

Add a sysfs interface to the SYSCTRL cell in the HiSilicon Hi5671Y
"luofu" SoC (0x10100000 + 0x0c08 on this board) that records the A/B
firmware pair (kernela + rootfsa, or kernelb + rootfsb).

The stock loader selects the pair from its environment (bootflag) and
uses the cell as its record of the pair: before Linux starts it stores
the opposite pair's low byte (0x11 for an A boot, 0x10 for a B boot), and
a boot that reaches userspace has to re-record the running pair or the
next reset takes the loader's failover path and switches back.  The
important encodings are therefore 0x10 (A recorded), 0x11 (B recorded)
and 0x00 (the value a true power-on clears the cell to); 0x21 is the
project's measured bench handover value, not a vendor one - vendor
userspace writes only 0x10/0x11 and the loader discards the 0x20 marker
bit on the same boot, so 0x21 never persists.

current_pair decodes the cell; next_pair accepts only the two measured
recorded-pair values and writes them with a low-byte read-modify-write
that preserves the upper 24 bits (exactly like the loader's own store and
the vendor sysenv driver) and verifies the whole cell read-back.  Probe
performs no register access, and the SYSCTRL page stays a shared syscon
with the machine-restart driver.

This interface is needed by the A/B sysupgrade path and by the target's
boot-time pair recorder; both are host-only so far.  It is an RFC: the
env-block re-stamp, the first boot of a written pair and the meaning of
the cell's upper 24 bits are not measured, and the sysfs ABI has to be
reviewed and frozen before it can be relied on.

Host-compiled against linux-6.18.60, binding checked with
dt_binding_check and checkpatch; never run on hardware.

Signed-off-by: ShibbityShwab <18537102+ShibbityShwab@users.noreply.github.com>

### 0010/26  power: reset: add Luofu machine restart driver

Status: RFC (provisional reset)

~~~
power: reset: add Luofu machine restart driver

Add a restart driver for the HiSilicon Hi5671Y "luofu" SoC.  The SoC has
no ARM architectural reset that takes the whole chip down; the vendor
sequence saves the SYSCTRL A/B boot-selector cell, asks the CRG for a
software reset and falls back to the CRG watchdog if the command does
not take.  Both pages are syscon nodes shared with the CRG/watchdog and
boot-selector drivers, so this driver never maps or claims MMIO itself.

Measured facts: the selector cell at SYSCTRL+0xc08 uses 0x10 for the A
pair and 0x11 for the B pair and is sticky across resets, so the driver
writes back only the value it has just read (a write-same) and leaves
unrecognised values alone; it therefore cannot move the board to another
slot.  The CRG reboot command pair is the vendor devicetree's own value
and is PROVISIONAL: the write order and register width have never been
measured.  It is confined to the reboot word and bounded by a 1 s
watchdog fallback instead of parking forever, which is exactly the
failure mode that stranded the board on the bench.

This is an RFC: the reset sequence must be validated on hardware with
recovery armed before it can be merged.  Probe performs no register
access; never run on hardware.

ARM: mach-hisilicon: add Hi5671Y SMP bring-up support

Add platform SMP bring-up for the HiSilicon Hi5671Y "luofu" SoC
(Cudy WR3000 v2.0, board R116).  The second Cortex-A9 is released by a
devicetree CPU enable-method registered as "hisilicon,luofu-smp" in a

The release sequence is decoded from the stock vendor kernel's private
"hisilicon,hsan_smp" method and its base devicetree; two independent
vendor builds (5.10.201 2.4.15 and 2.5.24) carry an
instruction-identical release body.  opensource/docs/SMP-RE.md carries
the evidence trail: recovered vendor symbol table, hsan_smp_ops,
hsan_boot_secondary and the vendor /cpus, SYSCTRL and CRG properties.
The release is:

  1. write __pa_symbol(secondary_startup) into the SYSCTRL pen word at
     SYSCTRL + 0xc00 (vendor DT smp-offset = <0xc00>);
  2. read-modify-write the CRG resume word at CRG + 0x38 (vendor DT
     resume-offset = <0x38>), clearing the two resume bits of the target
     core: 0x16/0x18 for CPU0 and 0x17/0x19 for CPU1 (vendor DT
     core-info = <0x16 0x18 0x17 0x19>);
  3. send the IPI_WAKEUP wakeup IPI to the target core.

There is no SMC, PSCI or secure-monitor call in the decoded release
path.  The vendor operations table has no prepare, secondary-init or
hotplug operation, so this port enables the Cortex-A9 SCU itself (the
mainline mach-hisi idiom) and maps the two syscon pages by their
existing compatibles before the release.  The register offsets and the
resume-bit numbers are SoC facts kept as driver data with the vendor
property citations; no new devicetree binding, property or YAML is
introduced.  The machine Kconfig help text, the Makefile and the
machine-descriptor comment are updated accordingly.

The method name is deliberately "hisilicon,luofu-smp", not the vendor
string "hisilicon,hsan_smp": the vendor string names their internal
board family, and a devicetree that still carries it simply does not
match and boots UP.  Without a matching method, or when either syscon
node is missing, the code stays inert: smp_boot_secondary() returns
-ENODEV and never writes a guessed pen address.

The release implementation is complete and was verified on hardware on
2026-11-21.  With the loader hand-off devicetree contract in place, the
stock U-Boot bootfip staging completes and CPU1 consumes the real
secondary_startup pen, giving "smp: Brought up 1 node, 2 CPUs", CPU1
mpidr 80000001, /proc/cpuinfo = 2 and a 2-CPU userspace (15-minute soak,
reboot persistent).  The kernel release code was correct all along; the
earlier "CPU1 failed to come online" results were caused by the loader
hand-off staging being aborted by two missing devicetree nodes in the
board DTS (aliases/console and reserved-memory/flashinfo@80600000 with
atag-offset = <0x1000>), measured on 2026-11-21 and recorded in
opensource/docs/SMP-RE.md section 24.

Important dependency: this patch is necessary but not sufficient.  The
enable-method, the console alias and the flashinfo reserved-memory node
are all board-DTS content and are not part of this kernel series.  The
dependent upstream DTS-series entry is
`dts-series/0001-arm-dts-hisilicon-luofu-r116-loader-handoff.patch`
(DTS-0001: adds `arch/arm/boot/dts/hisilicon/luofu-r116.dts` with the two
hand-off nodes; documented in `06-dts-series-dependency.md`).  Post the
DTS entry together with, or before, this patch; without the enable-method
the boot stays UP, and without the two hand-off nodes CPU1 is never
brought into the loader's pen-poll loop and the release has no consumer.

The patch remains an RFC for upstream review.  The target image that
carries it is bench-verified (2 CPUs, wired LAN through the documented

## Status legend

- ready-for-review: no known design blocker; the implemented subset is
  backed by a citable artifact and probe does not write unverified
  hardware.  Still has no hardware validation (read the cover letter).
- RFC: a known unverified/provisional write path, an open design
  question, or an interface that has to be reviewed first.
- RFC (partial, refuses probe) / draft (do not merge): explicitly not
  mergeable; posted for direction only.
- draft (do not merge; arm-gated data path): 0020 is the first patch
  that contains writes to the PIE engine.  They are reachable only
  through the kernel command line opt-in luofu_pie.arm=1, the probe
  refuses before the first write otherwise, both devicetree nodes stay
  disabled, and the armed path has never executed.  RX completion
  decode is still [U].
- draft (do not merge; read-only baseline probe): 0021 never writes a
  register, enables no clock and drives no reset; it validates the
  measured LSW baseline and the derived qid maps read-only and always
  refuses probe.  The attended W2-W6 write campaign is still owed.
- draft (do not merge; gated W3/W4/W5 write path): 0022 keeps the 0021
  default read-only.  With the module parameter luofu_lsw.arm=1 it
  enables the two LSW gate clocks and releases the four resets (W3) and
  snapshots the measured state read-only; luofu_lsw.arm=1 with
  luofu_lsw.qidmap=1 also programs the reviewed W2 qid-map write set for
  the populated rows, with a pre-write conformance gate, a readback of
  every programmed word and a restore on mismatch.  Neither gate has
  ever been passed on hardware; the W3 power-up, the W4/W5 effect and
  the EQM/classifier/VLAN formats are [U].
- draft (do not merge; netdev readiness only): 0023 registers a GEMAC
  netdev only when the PIE backend is armed and the LSW egress map is
  ready, fixes the phylink type so the carrier follows the netdev, and
  takes the MAC address from the devicetree or a random fallback.  The
  only MAC writes are the measured 1 Gbps link-up/link-down words; the
  RX completion decode and the TX-to-egress mapping are still [U] and
  the registration has never run on hardware.
- draft (do not merge; arm-gated completion decode): 0024 decodes the
  recovered v250 RX completion descriptor and builds the full normal
  non-TSO TX descriptor, and delivers received frames to the GEMAC
  net_device that registered the switch port.  Every PIE register write
  stays inside the existing luofu_pie.arm=1 arm path, the GEMAC
  hisilicon,port property and the port registration add no register
  write, and the arm path has never run.  The decode has never been
  observed on hardware: the field positions are [V] from the vendor
  disassembly but live values are unobserved, the two RX flag classes
  are [U] and the ring-index reading is [I].
- draft (do not merge; gated W4 egress write stage): 0025 adds the
  luofu_lsw.egress=1 stage between 0022's W3 power step and its W5
  qid-map write: the R1/R3/R5 probe-configuration words with a
  pre-write conformance gate, expectations derived from the pre-write
  snapshot, readback of every word and restore on mismatch.  It
  requires luofu_lsw.arm=1 and tightens readiness so both the probe
  configuration and the qid map must verify; the gate has never been
  set, no switch register has been written by this code, and the
  per-frame egress selection and the EQM/classifier/VLAN formats are
  still [U].
- draft (do not merge; MAC nvmem source, readiness-gated): 0026 makes
  the GEMAC netdev take its address from the read-only bdinfo MTD
  nvmem cell (fixed-layout/mac-base, LAN = base, WAN = base+1),
  defers probe when the provider is not registered yet and keeps the
  logged random fallback otherwise; userspace MAC assignment stays
  functional.  It registers nothing unless the 0023 readiness gate
  passes, writes no register or flash, and the nvmem read path has
  never run on a booted target.
- RFC (attended): host-validated platform code whose acceptance requires
  a single-variable, recovery-armed bench session; not part of the
  UP-first mergeable set.
- ready-for-review (read-only clock tree): the provider only exposes read
  paths (no set_rate/set_parent write path).  Its PLL rate equation and
  mux/gate parents are decoded from the vendor module/devicetree and have
  never been measured on the board, so those values stay unmeasured until
  the read-only bench readback.
